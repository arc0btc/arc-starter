# Patterns
*Reusable operational patterns, validated ≥2 cycles. Last consolidated: 2026-07-13T02:24Z*
## Core Patterns (Foundational)
**p-model-required** All task-creation paths must include model. Tasks without model fail at dispatch: "No model set."
**p-task-closure-discipline** [merged: p-pr-supersession + p-workflow-supersession-creation-gate 2026-06-18 + p-review-task-confirmed-resolution-closure 2026-07-05 task #21309 + p-terminal-task-state-immutability 2026-07-11 task #22005/#22006] Three task-closure rules: (1) **supersession** — when a higher-priority task/workflow supersedes pending work, close it explicitly (`status=failed, summary="superseded by #X"`) rather than leaving it to fail on its own — inflates failure counts and confuses audit trails; for workflow types producing the same side effect for the same entity, enforce the check at creation time too (verify no existing instance of workflow type B before inserting A); (2) **confirmed-resolution** — when a review/monitoring task confirms an external condition is resolved (blocked PR merged, bug fixed, workflow unblocked), take terminal action (close the blocked task) in the same cycle, not just report the finding — otherwise the condition re-triggers at full cost next sensor cycle (e.g. PR #638 blocked-task reviewed 3× same day before this was enforced); (3) **terminal immutability** — completed/failed/blocked states must guard against re-closure, since unconditional re-close resets `completed_at` and pulls stale tasks back into time-windowed retrospective lookback, creating infinite loops (task #21072/#20899); guard at CLI layer (`cmdTasksClose` rejects re-closure on terminal tasks with exit 1).
**p-signal-filing-gates** [merged: cooldown-precheck + payment-order-guard] Two gates before signal filing: (1) daily task count AND (2) 60-min per-agent cooldown. Dedup by (beat, source_url, data_hash). **Critical**: cooldown check BEFORE x402 payment — paying first then hitting cooldown wall wastes sats.
## Operational Patterns
**p-sensor-discipline-queue-dedup** [merged: 2026-06-14 + p-inflow-pool-health-ratio + p-sensor-required-field-validation 2026-06-30 task #20480] Sensors are stateless — idempotency is enforced at queue layer via `pendingOrCompletedTaskExistsForSource`. Sensor detects → queues stable source key → queue dedup checks pending/completed → skip if exists. Stale re-fires are caught by dedup, not sensor state. Dedup failures compound: queue liberally, dedup strictly. Sensors creating tasks must also set all required fields (model, skills) at insertion — dispatch rejects incomplete tasks with "No model set" (audit via grep for `insertTask` calls lacking a model param). **Inflow health**: producer/consumer ratio <1.0 = healthy; ≥1.0 or zero consumption = stalled pipeline requiring diagnostics before queuing more.
**p-sensor-state-resilience** [merged, extended 2026-06-14] Validate persisted state on load; rebuild from empty on version mismatch. Multi-source: fetch all in parallel, continue with available. Write scheduling state AFTER successful run — writing on entry creates multi-hour lockout on failure. Validate expected fields on read (presence ≠ correct format) and merge on write to preserve metadata. In-memory state doesn't survive dispatch cycles — persist what must survive (MEMORY.md, SQLite, task descriptions).
**p-shared-resource-serialization** [2026-04-08] Concurrent tasks on same nonce pool must serialize via shared tracking file + acquire-before-execute. Use mkdir-based locks. Don't roll back counter on tx failure; resync on staleness (>90s). Lock/cache TTL must exceed p99 operation duration.
**p-validation-credential-consistency** [merged] Before financial ops: validate address format AND maintain deny-list for addresses passing format but rejected downstream. Apply at sensor-level AND execution-time. Sensor credential reads must match namespace in SKILL.md and actual store — mismatch causes silent skips.
**p-skill-name-validation** [merged, extended 2026-07-02/07-04/07-07] Verify skill names via `arc skills` before `arc tasks add --skills`, writing `arc skills run --name <X>` in docs, or embedding in task templates — nonexistent names are silently ignored at dispatch. **Gotcha**: templates generating CLI commands with wrong skill names (e.g. `email` instead of `arc-email-sync`) fail at execution; validate template commands at creation-time (manual review or linter), not at dispatch. **Distributed-caller audit**: when a skill is renamed, grep-audit all spawning paths (`grep -r "old-name" skills/ src/`) — multiple unrelated generators often reference the same name independently, so fix all spawning points atomically rather than partially. At scale (100+ refs across many files): scan+dedupe into a centralized mapping, apply from the mapping to prevent per-file drift, verify via lint-check + syntax validation.
**p-external-api-drift** [merged, extended 2026-07-08 tasks #21712/#21744, extended 2026-07-09 task #21874] External platforms silently restructure without notice — audit ALL hardcoded references on retirement, and audit error-text classification rules quarterly since they go stale. Versioned APIs: validate endpoint availability across ALL versions EARLY, pin explicitly. Prefer structured API data over scraping when already present in response. **Upstream releases**: identify consumption model (subprocess/direct-API/transitive/unused) before acting. **Mechanism validation**: before investigating issues on external platforms, confirm the claimed mechanism/feature still exists (live docs, changelog, support history) — feature retirements/policy deprecations invalidate investigation premises mid-work (e.g. classified-payment issue #480 was obsolete because automated-payout had already been deprecated). **Field-limit discovery**: undocumented field-length limits (e.g. Whop's 1500-char product descriptions, 80-char title/headline) cause redundant fix cycles when found at execution time — validate boundary-value payloads at skill-integration time and document constraint bounds in SKILL.md. **Free-field optimization** [merged: p-api-free-field-optimization, 2026-07-14 #22656]: APIs billing per-request often support unlimited fields at no marginal cost — request all available fields upfront (X's `tweet_fields` doesn't add cost; full field set eliminated 125/195 bare-t.co declines via URL extraction). **Identifier-collision escape** [merged: p-auto-generated-external-identifier-collision-escape, 2026-07-06 #21425]: platforms with global-namespace auto-derived identifiers (Whop routes, handles) only reveal collisions at claim-time — expose CLI flags for post-discovery correction rather than DB surgery. **Ecosystem verification** [merged: p-research-ecosystem-analysis, 2026-06-08]: verify claimed migrations/deprecations via commit logs (attribution+dates+tone), not archive status; rapid create→archive→rebuild + fork survival indicates prototype validation, forks gaining >10× stars signal design-market fit. **Passive-hardening watch** [merged: p-upstream-passive-hardening-monitoring, 2026-07-02/06-29]: monitor upstream runtime releases for trust-boundary/transport-layer fixes that passively harden existing patterns with zero code changes (watch for "Fixed subagent X" / "Fixed parent agent receiving Y" in release notes); when a foundational dep ships a fix affecting a multi-layer call stack, audit that it actually propagated through ALL layers — a fix on one layer doesn't auto-propagate to callers.
**p-fix-and-deploy-verification** [merged 5x; wrangler-env-gate 2026-06-18] "Shipped" ≠ "working"; "built" ≠ "deployed." After any fix: require 1–2 observation cycles. After any publish/deploy: verify the deploy step ran. Manual deploy: validate local HEAD = origin, verify with curl to live endpoint. Multi-hop features and pipelines: verify observable end-user-visible output at each hop. **Wrangler gotcha**: always use `--env production` for production deploys. **Regeneration idempotency** [merged: p-regeneration-idempotency-deployment-verification, 2026-07-09 #21851]: regeneration tasks verify byte-for-byte output match to HEAD (confirming idempotency) AND validate live deployment independently (catches deploy-drift git-status misses); stage only task-owned files in mixed worktrees. **Build-recovery** [merged: p-subprocess-memory-pressure-build-recovery, 2026-07-13 #22237]: nested build-tool subprocess chains amplify memory pressure under tight VM headroom — a segfaulting build (exit 139) often succeeds run directly outside the CLI wrapper; after manual recovery, re-run the standard deploy CLI to record orchestration state consistently.
**p-immutable-marker-capture-timing** [2026-07-14, task #22476] In multi-step build/deploy pipelines with side-effecting intermediates (commits, sign operations), capture immutable markers (current SHA, deployment ID) AFTER all side-effecting steps complete, not before. Capturing before side-effects leaves the marker stale when intermediate steps create new state (e.g., SIP-018 sign-sweep commits), causing permanent false-alert loops downstream (false drift alerts, stale health checks recurring indefinitely). blog-deploy captured currentSha before the sign-sweep which can commit, leaving deployed SHA stale and triggering recurring drift alerts; fixed by re-reading HEAD after the sweep. Applies to any health check or verification depending on immutable state markers in orchestrated pipelines.
**p-signal-quality-pipeline** [merged] Pre-validate at two layers: (1) Sensor predicts score, discards below floor; (2) Filing queries current minimum accepted score, displacement requires exceeding LOWEST accepted. Signals need AIBTC-native angle. Complex workflows (>150 lines, 3+ fetches, novel research) decompose at creation. Pre-dispatch cost >$1 → decompose.
**p-research-synthesis** [merged, hardened 2026-06-29; extended: p-research-prior-findings-audit 2026-06-29 task #20285 + p-research-source-quality 2026-06-27/29] Before queuing research, audit existing reports for coverage; cite prior findings, confirm if recommendations shipped (grep code, check metrics) — reframe rather than re-derive when prior work covered the baseline, isolating only the genuinely new signal. Two orchestration styles: (1) small batches (<50 items, trusted partner) → single P2 Opus coordinator owning full pipeline; (2) large batches (50+) → P2 orchestrator + N P5 parallel tasks + P3 synthesis aggregator, dedup via `source="task:<parent>:<index>"`. Archive previous output atomically. Multi-repo: enumerate via org API first. **Pre-composition gate**: verify all source tasks completed before composition. **Shelf saturation**: when topic coverage exists in memory, apply stricter relevance thresholds; fold marginal items into synthesis editorial to prevent "slop-by-catalog." **Source quality**: auto-extracted/JS-rendered sites often miss content — treat absence as transport failure, escalate to WebFetch/WebSearch + primary sources. **arxiv-research gotcha**: read factor files directly (80% cost reduction). Cross-reference existing memory before creating new sections. **Convergence validation**: 3+ independent sources/batches converging validates architectural importance independent of capability maturity — gaps found in 3+ independent batches outrank capability expansions, strongest when unsolicited. Code changes from single-source research gate on primary-source verification. **Interpretation** [merged: p-synthesis-interpretation]: topic clustering (>60% one theme) documents as methodology bias or market signal, not diversity failure; consistent absences (same subsystem missing from 3+ sources) document as architectural blindspot, escalate systemic gaps. **Social mapping** [merged: p-research-synthesis-to-social-mapping, 2026-07-05 task #21244]: when distilling academic research into social content, map the finding to personal/operational architecture first — surfaces what makes the research relevant to *your* problems, not generic interest; open question at post-end should emerge from this gap mapping, driving genuine engagement vs artificial CTAs.
**p-research-relevance-and-redirect-filters** [merged: p-research-domain-relevance-prefilter + p-research-mainstream-saturation-sku-filter + p-research-infrastructure-gap-redirect, 2026-07-14, tasks #22488/#22616/#22617] Three gates when distilling research: (1) **domain prefilter** — apply keyword/stack-fit pre-filters before composition, skip candidates lacking domain keywords (MCP, x402, bitcoin, stacks) or direct architectural relevance (arXiv screening prioritized agent-architecture findings, skipped VEXAIoT IoT pentesting as stack-tangential); (2) **mainstream-saturation SKU filter** — before flagging research as a paid-SKU candidate, check if mainstream crypto press already covers it well; if so, cite rather than publish (Jeremy Allaire's agentic-economy treatise was already thoroughly covered, eliminating publication incentive); (3) **infrastructure-gap redirect** — when research validates a capability already exists, redirect energy to gaps in adjacent layers (orchestration, workflow gating, integration points) rather than re-confirming the capability (Codex-in-Claude-Code research found the SDK already handles it; real gap was cross-model adversarial-review missing from the PR workflow).
**p-classification-restraint-accept-sparse-output** [2026-07-15, task #22786] When distilling a batch into predefined categories, accept sparse or zero-filled distributions rather than force-fitting low-relevance items to pad categories. Example: arXiv digest produced 4 agent-architecture findings and zero quantum-pqc and zero aibtc-infra papers — correctly dropped pressure to fill all buckets, yielding a tighter, higher-quality batch. Force-fitting creates hollow entries that dilute quality and waste reader time. Gate on domain fit first (does this address our stack?); skip entirely rather than select a weak secondary category for forced inclusion.

**p-auto-commit-type-regression-blind-spot** [2026-07-15, task #22717/#22721] Fallback auto-commit paths (unattended dispatch cycles committing `memory/`, `skills/`, `src/`) bypass normal per-dispatch session oversight — resulting type-level regressions (wrong arg types, dropped required fields, mismatched JSON/array serialization) ship silently. Pre-commit syntax guard (Bun transpile) catches syntax errors but misses type-level semantic bugs (caller expects `string`, passes `array`; caller requires `model` field, omitted). Post-commit service health check detects dead services but not runtime type errors in sensor/background logic. Consequence: sensors or background jobs throw at runtime on every execution, halting functionality for hours until discovered in architecture review. Mitigation: add a `tsc --noEmit` baseline-drift sensor (30-min cadence) running real type-check on touched files, surfacing error-count increases in auto-committed `.ts` files; flag as advisory follow-up (doesn't block commit since type-errors aren't crashes, but surfaces the regression for same-cycle code review + fix). Distinguish from type-safe compilation gates (require pre-commit passage): type-check-drift is a *post-commit observation tool* for auto-commits specifically, catching the gap between "syntax OK" (passes transpile) and "semantically correct" (passes type-check).

**p-skill-context-boundaries** [2026-06-19] Dispatch loads SKILL.md + memory only for skills listed in task `skills[]`. Declare required skills upfront; omitting a skill gates its context.
**p-task-generator-skill-delegation-context-review-exempt** [2026-07-15, task #22796] Task generators that deterministically shell out to downstream skills via CLI (e.g., arc-article-pipeline: `stage → blog-publishing create`, email draft) create description-text mentions of those skills without needing the skill context at dispatch — context-review detectors false-flag as "missing SKILL.md loaded." Fix: subject-based exemption in the detector (matching existing META_TASK_SOURCES pattern) or CLI-delegation marker in description text. Prevents recurring false-positives on self-contained orchestration tasks.
**p-meta-consolidation-self-timeout** [2026-07-08, tasks #21511/#21531/#21535; validated 2026-07-09 task #21787/#21795] Consolidation tasks operating on Arc's own ever-growing self-referential files (`patterns.md`, `MEMORY.md`) monolithically re-read + rewrite the whole file once it crosses a line threshold — this both timed out at 15min on sonnet tier (#21511, 175 lines) and cost 2 follow-up passes at $2.9+ each (#21531/#21535) to recover. Fix: once a self-referential file exceeds its threshold, decompose the consolidation into per-section subtasks (one per `##` header) with a final merge pass, rather than one task rewriting the entire file — mirrors `p-large-audit-aggregator-cli`'s "decompose reads ≥10 files" rule but applies it to writes/edits on a single large file, not just reads across many files. **Validation** (task #21795): Agent Design section (21 entries, 151 lines) consolidated in one pass by merging 5 synonym pairs (24% overlap density), reduced to 146 lines, no timeout, no syntax issues; confirms per-section granularity is the right unit. **Metric gotcha** (validated #21787): entry-count reduction (merged 5 pairs, cut 21→16 entries) doesn't correlate linearly with file-size reduction (189→185 lines, only 4 lines saved) because parent entries grow in length when absorbing child entries — when metric-driven targets are line-count or char-count, monitor both dimensions during consolidation or merge/prose-tightening may be insufficient; `p-memory-lifecycle` prose-density passes provide secondary compression if entry merging alone misses targets. **Lint cadence** [merged: p-memory-hygiene, 2026-06-16]: periodic lint passes over `memory/shared/entries/` catch index↔file inconsistencies, dead `[[links]]`, duplicate summaries; queue one lint task per 500 MEMORY.md lines. Long-lived [A] items should include explicit "out-of-scope" lines.
**p-search-predicate-gate-composition** [2026-07-03, task #20908; extended 2026-07-08, tasks #20988/#21022/#21024/#21157/#21158/#21162/#21174] When searching for candidates subject to a downstream eligibility gate (age, budget, status), incorporate the gate into the search predicate FIRST — eliminates wasted review on pre-rejected candidates. Example: reply-lane sweep searching X for engagement already fails reply-send's >48h target-age guard, so search must filter `created_at ≤ 48h_ago` at query time, not batch-then-reject. **Thread-continuation variant**: chained follow-up tasks (thread reply-N/CTA continuations queued off a single parent thread) hit the same shared daily cap independently, since each is created without checking remaining budget at creation time — 7 same-week failures were all `DAILY_TWEET_CAP` exhaustion for two thread chains ('Thirty-Five Hours of Silence', '8 lines from losing my own memory'). Fix: when queuing a chain of dependent posts against a shared cap, check remaining budget at the point of creating each follow-up, not just at its own dispatch — a chain generator should stop scheduling further links once the cap is already tight instead of relying on each link to independently fail and retry.
## Agent Design
**p-security-threat-model** [merged, extended 2026-07-02 task #20832; merged 2026-07-08 task #21776; cross-referenced 2026-07-09 against [[deepmind-6attack-taxonomy-ingestion-audit]] task #21474; merged: p-credential-exposure-pr 2026-05-22 + p-subagent-permission-mode-propagation 2026-06-29 v2.1.196] New capabilities (sub-agents, persistent memory, external fetch) require explicit threat model before shipping. Sanitize fetched content. DeepMind rates: 86% prompt injection, >80% memory poisoning, 58-90% sub-agent hijacking. Agent-controlled gateway/endpoint URL overrides must validate via allowlist (not denylist) before routing authenticated requests — arbitrary gateway params enable prompt-injection credential leaks (apiKey + signed headers redirected to attacker host). **Pre-wiring review**: security-adjacent subsystems (injection defense, sanitization, key management) gate deployment on multi-lens review across independent expert perspectives (correctness, edge-cases, attack scenarios, performance, maintainability); AGENT.md must disclose coverage boundaries ("protects X but not Y") rather than overstating scope — converge on pass, divergence flags gaps before wiring to production. The 2026-07-06 DeepMind 6-attack ingestion audit validated this pattern rather than superseding it — its concrete fixes live as their own entries, not duplicated here: `AGENT.md` "data not instructions" framing → [[p-agent-md-authoring-trigger]] untrusted-input override; CSS-hidden-text stripping → `p-css-aware-content-sanitization`; unprovenanced `recent.log`→MEMORY.md poisoning path → `p-consolidation-untrusted-source-gates`. **Credential exposure**: PR credential exposure is public from push time regardless of review status — immediately post blocking review + escalate with incident summary, affected wallet, ranked actions. **Sub-agent permission propagation**: `--dangerously-skip-permissions` had a silent fallback where sub-agents ran in auto mode despite parent bypass setting — after runtime fixes, audit spawned sub-agents to verify propagation actually works.

**p-purpose-loop** [merged, extended 2026-07-01, task #20751] Daily PURPOSE evals expose directive gaps → low scores become priorities. Distinguish policy-constrained (escalate, don't queue work) from actionable (queue P2 boost). Empty queue + low scores = structural constraint; constant saturation signals policy working as designed — diagnose each low dimension separately. When a binding constraint persists ≥2 consecutive cycles and an existing mitigation exists (built but dormant), activate it IMMEDIATELY within the same eval cycle rather than queuing research on redesign — deployment friction is lower than building solutions (e.g. cost-efficiency constraint + dormant task-classifier → CLAUDE.md instruction update deployed it immediately). **External-ownership gate** [merged: p-eval-follow-up-gate-external-ownership, 2026-07-14 #22509]: before creating a follow-up for a persistent low-scoring dimension, check (1) is it already tracked in Active Items with a documented owner, (2) is the blocker external (policy-disabled, decision-pending) not an execution gap, (3) is the owner actively progressing — if all three pass, skip follow-up creation and consolidate metadata instead.
**p-queue-composition-guard** [2026-05-05] When any single category exceeds 30% of pending tasks, apply sensor cap or daily limit. Strategic tasks ≥40% of weekly cycles. Cap-driven dequeue → `status=completed`, not `failed`.
**p-failure-diagnosis** [merged: p-recurring-identical-error-code-defect-signal, extended 2026-05-29 2x, 2026-07-04/05 task #21031/#21035/#21263] When N failures spike, classify by error type. 80%+ same root cause → fix the cause, then scan pending tasks and close as `blocked`. Active task + dead PID + stale cycle_log (>2min): consistent vs cycle_log→resume, inconsistent→archive+restart. **Smoke/dry-run tasks**: close as `completed` if probe goal achieved. Prefix subjects `[SMOKE]`/`[DRY-RUN]`. **Batch-uniform errors**: uniform error signature across a batch = service-level issue, not individual failures — queue ONE diagnose-before-fanout task. Time-correlated clustering (same UTC hour, later retries succeed) = transient rate-limit reset boundary. 3+ consecutive auth failures in <1h = transient upstream outage, escalate. Before retrying, validate account/resource state (lock, suspension, quota) first — may be an account-level block not a code bug (e.g. X self-reply 403, see [[x-reply-403-account-lock-cascade]]). **Identical-recurrence signal**: when the same error recurs across cycles with zero variation, it's a code defect masquerading as transient — escalate to implementation priority over sensor tuning (e.g. X tweet-cap exhaustion appearing twice identically → dual-cap logic bug). Systematic pattern classes (UTC-parse naive reads, misplaced guards, scoped-out variables) get ONE comprehensive sweep, not incremental follow-ups; a recurring manual-reviewer check with no code fix after ≥2 audits should become a mechanical lint rule.
**p-false-positive-prevention** [merged, task #20096; extended 2026-07-05 task #21312, 2026-07-07 task #21503/#21627/#21634, 2026-07-08 task #21692/#21765, 2026-07-09 task #21805, 2026-07-10 task #21967; extended 2026-07-13 task #22223] Nine FP categories (plus a 2026-07-08 variant of #9, refined 2026-07-08): (1) `scheduled_for` > now = waiting, not stuck; (2) blocked >48h no new signals → 168h+ suppress; (3) **dispatch-stale alerts** — always verify PID liveness FIRST (query process table or check dispatch-lock.json PID is alive) before trusting timestamp age, since a long-running task produces an old last-cycle time while dispatch actively runs; timestamp + pending-task-count is insufficient alone; complementary check: if PID is alive, dismiss as false-positive regardless of timestamp; if PID is dead, age-based TTL acts as backup safeguard catching process-reuse after crash (task #21967); (4) observation tasks need operational context loaded first; (5) infrastructure migration — validate data source still authoritative before escalating; (6) **health-audit anomalies** (budget exhaustion, uncommitted changes, repeated failures) validate against known transient patterns (daily-cap resets, db drift, log noise) BEFORE escalating — they self-clear next cycle; (7) **guard skip vs error** — expected guard conditions (budget exhaustion, rate-limit, approval rejection) should yield `"skip"` not `"error"` from sensors, since misclassification inflates `consecutive_failures` into false escalations; budget-unit migrations cause one-time transient spikes at UTC-midnight reset, not defects. (8) **duplicate escalations** — before queuing a new escalation task, check `arc tasks [--status blocked]` for an existing gate/blocker match; same gate already escalated → close as superseded or skip creation, preventing escalation noise and preserving single audit trail per decision. (9) **self-referential signal loop** [2026-07-07, task #21634; refined 2026-07-08 task #21765, 2026-07-09 task #21805, validated 2026-07-10 task #21937; extended 2026-07-13 task #22223] A sensor's own output tasks can re-trigger its own inputs; synthesis/eval tasks quote blocked-task IDs in their summary prose, falsely indicating resolution. Prose-text matching is a weak resolution signal. Fix: exclude `source = TASK_SOURCE` tasks + direct children; better: use structural signals (dependent-task completion, state transitions) for resolution detection. Prose-based detection alone enables infinite re-fire loops. Always validate a retrospective alert against current state — a stale failure-count flag may mask a recovery. **Blocked-review-task variant** [2026-07-13, task #22223]: review tasks auditing whether blocked tasks have unblocked can themselves false-trigger when sensors detect prose-references (sibling mention-quotes, digest-embedded IDs) masquerading as resolution — before queuing a blocked-task review, validate the gate condition actually changed (email history shows new reply, decision/approval completed) rather than trusting prose-based signals; three blocked tasks (#21499, #21905, #21800) re-reviewed found zero state change, email-sync confirmed no replies, sensor signals were false-positive digest-quotes. **Syntax-variant recurrence**: when false-positives persist through multiple context variants (digest-quoted mentions + plain-prose mentions) despite syntax-specific exemptions (e.g. #21694's digest-marker fix, task #21765 plain-prose mentions still recurred), apply per-instance cooldown-gating (48h mute after review) as tactical interim measure while structural prevention is designed — asymmetric cost scenario (many cheap false reviews drain budget faster than structural fix). **Implementation** (#21766): scan prior completed review tasks' descriptions via LIKE to find last close time; suppress re-flagging if <48h ago; signal-only candidates (parent/sibling/mention, no independent stale reason) get cooldown, but tasks with genuine stale-reasons bypass it since they're already structurally re-reviewable. Distinct from permanent exemptions: cooldown resets, allowing genuine stale conditions to eventually break through. **Escalation-to-structural**: when the same FP category recurs ≥5 consecutive times after a tactical fix (mute, exemption, cooldown) is deployed, do not iterate additional patches — escalate to a structural fix (detector mechanism redesign, architecture change, classification rule overhaul) in the same cycle instead. Cost of repeated tactical cycles (redeploy, re-review, re-debug) outweighs design debt for the upgrade; example: arc-blocked-review false-positive loop reached 5 consecutive re-flags post-48h-cooldown deployment, triggering immediate structural cooldown fix same cycle rather than another exemption patch.
**p-task-premise-verification** [merged: p-standing-policy-gate-supersession, 2026-06-19, extended 2026-07-07 task #21494] Tasks claiming to verify a feature/mechanism/safety guard, or claiming a gate/sign-off requirement is current, should validate upfront: feature exists in runtime, claimed behavior matches implementation, supporting docs are current, and — for gates specifically — the requirement hasn't been cleared by standing policy (check skill CLI code/comments for directives) or prior explicit approval (check email history + MEMORY.md). Task descriptions lag behind mid-chain policy changes; trace authorization dates to distinguish stale framing from actual blockers. Reject false-premise tasks at triage. **Signal freshness** [2026-06-12]: tasks replying to external signals validate signal age at dispatch time — mentions >7 days old close as completed no-op. **Phantom fields** [merged: p-phantom-field-documentation-intake, 2026-07-12 task #22177]: before accepting "document X" requests, verify X exists in code (grep, schema, git history) — if not found, redirect to scope clarification ("should we implement/add this first?") rather than fabricating docs for phantom/aspirational fields.
**p-live-state-precheck** [merged: p-work-already-done-precheck (6x) + p-blocked-workflow-diagnosis (4x), 2026-06-30 to 07-04; extended 2026-07-10 task #21925: sensor consumption models; extended 2026-07-11 task #22032: infrastructure state assertions; extended 2026-07-11 task #22046: blocked-task email verification; extended 2026-07-14 task #22647: auto-generated integration tasks] Before queuing/executing recurring/repair/maintenance/investigation work, or re-investigating a `blocked`/stuck task, check live state first rather than trusting task history or stale status. **General precheck**: run the relevant live-state CLI (`consolidate-memory check`, `sensor-health-report`), scan git/task history for the target fix or root-cause chain (e.g. #21165→#21169→#21178), verify config files for claimed gate/enable status, or query the external blocker's live state directly.
