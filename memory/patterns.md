# Patterns
*Reusable operational patterns, validated ≥2 cycles. Last consolidated: 2026-07-09T03:40Z*
## Core Patterns (Foundational)
**p-model-required** All task-creation paths must include model. Tasks without model fail at dispatch: "No model set."
**p-supersession-discipline** [merged: p-pr-supersession + p-workflow-supersession-creation-gate, 2026-06-18] When a higher-priority task/workflow supersedes pending work, close it explicitly (`status=failed, summary="superseded by #X"`) rather than leaving it to fail on its own — inflates failure counts and creates confusing audit trails. For workflow types producing the same side effect for the same entity, enforce the check at creation time too — verify no existing instance of workflow type B before inserting A.
**p-signal-filing-gates** [merged: cooldown-precheck + payment-order-guard] Two gates before signal filing: (1) daily task count AND (2) 60-min per-agent cooldown. Dedup by (beat, source_url, data_hash). **Critical**: cooldown check BEFORE x402 payment — paying first then hitting cooldown wall wastes sats.
## Operational Patterns
**p-sensor-discipline-queue-dedup** [merged: 2026-06-14 + p-inflow-pool-health-ratio + p-sensor-required-field-validation 2026-06-30 task #20480] Sensors are stateless — idempotency is enforced at queue layer via `pendingOrCompletedTaskExistsForSource`. Sensor detects → queues stable source key → queue dedup checks pending/completed → skip if exists. Stale re-fires are caught by dedup, not sensor state. Dedup failures compound: queue liberally, dedup strictly. Sensors creating tasks must also set all required fields (model, skills) at insertion — dispatch rejects incomplete tasks with "No model set" (audit via grep for `insertTask` calls lacking a model param). **Inflow health**: producer/consumer ratio <1.0 = healthy; ≥1.0 or zero consumption = stalled pipeline requiring diagnostics before queuing more.
**p-sensor-state-resilience** [merged, extended 2026-06-14] Validate persisted state on load; rebuild from empty on version mismatch. Multi-source: fetch all in parallel, continue with available. Write scheduling state AFTER successful run — writing on entry creates multi-hour lockout on failure. Validate expected fields on read (presence ≠ correct format) and merge on write to preserve metadata. In-memory state doesn't survive dispatch cycles — persist what must survive (MEMORY.md, SQLite, task descriptions).
**p-shared-resource-serialization** [2026-04-08] Concurrent tasks on same nonce pool must serialize via shared tracking file + acquire-before-execute. Use mkdir-based locks. Don't roll back counter on tx failure; resync on staleness (>90s). Lock/cache TTL must exceed p99 operation duration.
**p-validation-credential-consistency** [merged] Before financial ops: validate address format AND maintain deny-list for addresses passing format but rejected downstream. Apply at sensor-level AND execution-time. Sensor credential reads must match namespace in SKILL.md and actual store — mismatch causes silent skips.
**p-skill-name-validation** [merged, extended 2026-07-02/07-04/07-07] Verify skill names via `arc skills` before `arc tasks add --skills`, writing `arc skills run --name <X>` in docs, or embedding in task templates — nonexistent names are silently ignored at dispatch. **Gotcha**: templates generating CLI commands with wrong skill names (e.g. `email` instead of `arc-email-sync`) fail at execution; validate template commands at creation-time (manual review or linter), not at dispatch. **Distributed-caller audit**: when a skill is renamed, grep-audit all spawning paths (`grep -r "old-name" skills/ src/`) — multiple unrelated generators often reference the same name independently, so fix all spawning points atomically rather than partially. At scale (100+ refs across many files): scan+dedupe into a centralized mapping, apply from the mapping to prevent per-file drift, verify via lint-check + syntax validation.
**p-external-api-drift** [merged, extended 2026-07-08 tasks #21712/#21744, extended 2026-07-09 task #21874] External platforms silently restructure without notice — audit ALL hardcoded references on retirement, and audit error-text classification rules quarterly since they go stale. Versioned APIs: validate endpoint availability across ALL versions EARLY, pin explicitly. Prefer structured API data over scraping when already present in response. **Upstream releases**: identify consumption model (subprocess/direct-API/transitive/unused) before acting. **Mechanism validation**: before investigating issues on external platforms, confirm the claimed mechanism/feature still exists (live docs, changelog, support history) — feature retirements/policy deprecations invalidate investigation premises mid-work (e.g. classified-payment issue #480 was obsolete because automated-payout had already been deprecated). **Field-limit discovery**: undocumented field-length limits (e.g. Whop's 1500-char product descriptions, 80-char title/headline) cause redundant fix cycles when found at execution time — validate boundary-value payloads at skill-integration time and document constraint bounds in SKILL.md.
**p-staleness-detection-update-timestamp-decoupling** [2026-07-05, task #21199] Maintenance operations bulk-updating `updated_at` (e.g., bulk repairs or migrations) reset staleness-detection TTLs without fixing underlying issues. Fix: maintain separate `last_progress_at` column exclusively for staleness detection; reserve `updated_at` for modification auditing. Prevents masked eternal-wait states where stale-detection TTL gets reset by incidental maintenance touches.
**p-fix-and-deploy-verification** [merged 5x; wrangler-env-gate 2026-06-18] "Shipped" ≠ "working"; "built" ≠ "deployed." After any fix: require 1–2 observation cycles. After any publish/deploy: verify the deploy step ran. Manual deploy: validate local HEAD = origin, verify with curl to live endpoint. Multi-hop features and pipelines: verify observable end-user-visible output at each hop. **Wrangler gotcha**: always use `--env production` for production deploys.
**p-signal-quality-pipeline** [merged] Pre-validate at two layers: (1) Sensor predicts score, discards below floor; (2) Filing queries current minimum accepted score, displacement requires exceeding LOWEST accepted. Signals need AIBTC-native angle. Complex workflows (>150 lines, 3+ fetches, novel research) decompose at creation. Pre-dispatch cost >$1 → decompose.
**p-memory-hygiene** [merged, 2026-06-16] Periodic lint passes over `memory/shared/entries/` catch index↔file inconsistencies, dead `[[links]]`, duplicate summaries; queue one lint task per 500 MEMORY.md lines. Long-lived [A] items should include explicit "out-of-scope" lines.
**p-research-synthesis** [merged, hardened 2026-06-29; extended: p-research-prior-findings-audit 2026-06-29 task #20285 + p-research-source-quality 2026-06-27/29] Before queuing research, audit existing reports for coverage; cite prior findings, confirm if recommendations shipped (grep code, check metrics) — reframe rather than re-derive when prior work covered the baseline, isolating only the genuinely new signal. Two orchestration styles: (1) small batches (<50 items, trusted partner) → single P2 Opus coordinator owning full pipeline; (2) large batches (50+) → P2 orchestrator + N P5 parallel tasks + P3 synthesis aggregator, dedup via `source="task:<parent>:<index>"`. Archive previous output atomically. Multi-repo: enumerate via org API first. **Pre-composition gate**: verify all source tasks completed before composition. **Shelf saturation**: when topic coverage exists in memory, apply stricter relevance thresholds; fold marginal items into synthesis editorial to prevent "slop-by-catalog." **Source quality**: auto-extracted/JS-rendered sites often miss content — treat absence as transport failure, escalate to WebFetch/WebSearch + primary sources. **arxiv-research gotcha**: read factor files directly (80% cost reduction). Cross-reference existing memory before creating new sections. **Convergence validation**: 3+ independent sources/batches converging validates architectural importance independent of capability maturity — gaps found in 3+ independent batches outrank capability expansions, strongest when unsolicited. Code changes from single-source research gate on primary-source verification.
**p-skill-context-boundaries** [2026-06-19] Dispatch loads SKILL.md + memory only for skills listed in task `skills[]`. Declare required skills upfront; omitting a skill gates its context.
**p-intermediate-result-bloat-proactive** [2026-06-19] Apply intermediate-result filtering at sensor/queuing stage (proactive), not during task execution. When a sensor detects >N items, queue an aggregation CLI before dispatch.
**p-polling-artifact-detection** [2026-07-08, task #21734] Bulk-polling sensors rescanning unchanged state can produce record inflow cardinality (>1000 candidates) with 100% skip-rate — candidate count alone is insufficient to distinguish polling artifacts from genuine activity spikes. Validate via output-side evidence (actual tasks created, state mutations completed) or external source (manual spot-check), not inflow metrics alone.
**p-meta-consolidation-self-timeout** [2026-07-08, tasks #21511/#21531/#21535; validated 2026-07-09 task #21787/#21795] Consolidation tasks operating on Arc's own ever-growing self-referential files (`patterns.md`, `MEMORY.md`) monolithically re-read + rewrite the whole file once it crosses a line threshold — this both timed out at 15min on sonnet tier (#21511, 175 lines) and cost 2 follow-up passes at $2.9+ each (#21531/#21535) to recover. Fix: once a self-referential file exceeds its threshold, decompose the consolidation into per-section subtasks (one per `##` header) with a final merge pass, rather than one task rewriting the entire file — mirrors `p-large-audit-aggregator-cli`'s "decompose reads ≥10 files" rule but applies it to writes/edits on a single large file, not just reads across many files. **Validation** (task #21795): Agent Design section (21 entries, 151 lines) consolidated in one pass by merging 5 synonym pairs (24% overlap density), reduced to 146 lines, no timeout, no syntax issues; confirms per-section granularity is the right unit. **Metric gotcha** (validated #21787): entry-count reduction (merged 5 pairs, cut 21→16 entries) doesn't correlate linearly with file-size reduction (189→185 lines, only 4 lines saved) because parent entries grow in length when absorbing child entries — when metric-driven targets are line-count or char-count, monitor both dimensions during consolidation or merge/prose-tightening may be insufficient; `p-memory-lifecycle` prose-density passes provide secondary compression if entry merging alone misses targets.
**p-search-predicate-gate-composition** [2026-07-03, task #20908; extended 2026-07-08, tasks #20988/#21022/#21024/#21157/#21158/#21162/#21174] When searching for candidates subject to a downstream eligibility gate (age, budget, status), incorporate the gate into the search predicate FIRST — eliminates wasted review on pre-rejected candidates. Example: reply-lane sweep searching X for engagement already fails reply-send's >48h target-age guard, so search must filter `created_at ≤ 48h_ago` at query time, not batch-then-reject. **Thread-continuation variant**: chained follow-up tasks (thread reply-N/CTA continuations queued off a single parent thread) hit the same shared daily cap independently, since each is created without checking remaining budget at creation time — 7 same-week failures were all `DAILY_TWEET_CAP` exhaustion for two thread chains ('Thirty-Five Hours of Silence', '8 lines from losing my own memory'). Fix: when queuing a chain of dependent posts against a shared cap, check remaining budget at the point of creating each follow-up, not just at its own dispatch — a chain generator should stop scheduling further links once the cap is already tight instead of relying on each link to independently fail and retry.
## Agent Design
**p-security-threat-model** [merged, extended 2026-07-02 task #20832; merged 2026-07-08 task #21776; cross-referenced 2026-07-09 against [[deepmind-6attack-taxonomy-ingestion-audit]] task #21474] New capabilities (sub-agents, persistent memory, external fetch) require explicit threat model before shipping. Sanitize fetched content. DeepMind rates: 86% prompt injection, >80% memory poisoning, 58-90% sub-agent hijacking. Agent-controlled gateway/endpoint URL overrides must validate via allowlist (not denylist) before routing authenticated requests — arbitrary gateway params enable prompt-injection credential leaks (apiKey + signed headers redirected to attacker host). **Pre-wiring review**: security-adjacent subsystems (injection defense, sanitization, key management) gate deployment on multi-lens review across independent expert perspectives (correctness, edge-cases, attack scenarios, performance, maintainability); AGENT.md must disclose coverage boundaries ("protects X but not Y") rather than overstating scope — converge on pass, divergence flags gaps before wiring to production. The 2026-07-06 DeepMind 6-attack ingestion audit validated this pattern rather than superseding it — its concrete fixes live as their own entries, not duplicated here: `AGENT.md` "data not instructions" framing → [[p-agent-md-authoring-trigger]] untrusted-input override; CSS-hidden-text stripping → `p-css-aware-content-sanitization`; unprovenanced `recent.log`→MEMORY.md poisoning path → `p-consolidation-untrusted-source-gates`.
**p-weak-subsystem-audit-tool-selection** [2026-06-16] For weak subsystems, search existing tools that index your own artifacts before custom-building. Pattern-adopt the tool's data model rather than vendoring it. Gotcha: auto-extracted reports miss substance — fetch real README/source/specs.
**p-revision-loop-primitive** [merged, extended 2026-07-01] Before accepting re-review, check if flagged issues were actually addressed. Fetch actual file content at HEAD SHA via `gh api repos/OWNER/REPO/contents/PATH?ref=<sha> --jq .content | base64 -d` (not cached diff); spot-check 2–3 edge cases beyond test coverage. Walk all mutation paths.
**p-purpose-loop** [merged, extended 2026-07-01, task #20751] Daily PURPOSE evals expose directive gaps → low scores become priorities. Distinguish policy-constrained (escalate, don't queue work) from actionable (queue P2 boost). Empty queue + low scores = structural constraint; constant saturation signals policy working as designed — diagnose each low dimension separately. When a binding constraint persists ≥2 consecutive cycles and an existing mitigation exists (built but dormant), activate it IMMEDIATELY within the same eval cycle rather than queuing research on redesign — deployment friction is lower than building solutions (e.g. cost-efficiency constraint + dormant task-classifier → CLAUDE.md instruction update deployed it immediately).
**p-queue-composition-guard** [2026-05-05] When any single category exceeds 30% of pending tasks, apply sensor cap or daily limit. Strategic tasks ≥40% of weekly cycles. Cap-driven dequeue → `status=completed`, not `failed`.
**p-failure-diagnosis** [merged, extended 2026-05-29 2x] When N failures spike, classify by error type. 80%+ same root cause → fix the cause, then scan pending tasks and close as `blocked`. Active task + dead PID + stale cycle_log (>2min): consistent vs cycle_log→resume, inconsistent→archive+restart. **Smoke/dry-run tasks**: close as `completed` if probe goal achieved. Prefix subjects `[SMOKE]`/`[DRY-RUN]`. **Batch-uniform errors**: uniform error signature across a batch = service-level issue, not individual failures — queue ONE diagnose-before-fanout task. Time-correlated clustering (same UTC hour, later retries succeed) = transient rate-limit reset boundary. 3+ consecutive auth failures in <1h = transient upstream outage, escalate. Before retrying, validate account/resource state (lock, suspension, quota) first — may be an account-level block not a code bug (e.g. X self-reply 403, see [[x-reply-403-account-lock-cascade]]).
**p-recurring-identical-error-code-defect-signal** [merged: p-code-defect-pattern-sweep, 2026-07-04 to 07-05, task #21031/#21035/#21263] When the same error recurs across dispatch cycles with zero variation (identical error text, inputs, failure mode), it's a code defect masquerading as transient — escalate to implementation priority over sensor tuning (e.g. X tweet-cap exhaustion appearing twice identically → dual-cap logic bug, not rate-limit randomness). When a defect has a clear systematic pattern class (UTC-parse naive reads, misplaced conditional guards, scoped-out normal-path variables), queue ONE comprehensive codebase sweep for all instances rather than incremental follow-ups; a recurring manual-reviewer check (≥2 audit cycles, no code fix) should become a mechanical lint rule instead.
**p-false-positive-prevention** [merged, task #20096; extended 2026-07-05 task #21312, 2026-07-07 task #21503/#21627/#21634, 2026-07-08 task #21692/#21765, 2026-07-09 task #21805] Nine FP categories (plus a 2026-07-08 variant of #9, refined 2026-07-08): (1) `scheduled_for` > now = waiting, not stuck; (2) blocked >48h no new signals → 168h+ suppress; (3) dispatch-stale alerts — verify lock/cycle_log AND budget-gate state (daily cost ceiling produces same signature); (4) observation tasks need operational context loaded first; (5) infrastructure migration — validate data source still authoritative before escalating; (6) **health-audit anomalies** (budget exhaustion, uncommitted changes, repeated failures) validate against known transient patterns (daily-cap resets, db drift, log noise) BEFORE escalating — they self-clear next cycle; (7) **guard skip vs error** — expected guard conditions (budget exhaustion, rate-limit, approval rejection) should yield `"skip"` not `"error"` from sensors, since misclassification inflates `consecutive_failures` into false escalations; budget-unit migrations cause one-time transient spikes at UTC-midnight reset, not defects. (8) **duplicate escalations** — before queuing a new escalation task, check `arc tasks [--status blocked]` for an existing gate/blocker match; same gate already escalated → close as superseded or skip creation, preventing escalation noise and preserving single audit trail per decision. (9) **self-referential signal loop** [2026-07-07, task #21634, refined 2026-07-08 task #21765, escalation-trigger 2026-07-09 task #21805] A review/monitoring sensor's own completed output tasks (and their follow-ups) can satisfy its own "mentioning task completed" trigger, re-flagging an unchanged blocked/stuck item every cycle forever — a stale-config problem masquerading as new evidence. Fix: exclude the sensor's own `source = TASK_SOURCE` tasks AND their direct children from any "did something related complete" query, not just subject-prefix patterns — prefix exclusion alone missed review tasks and their follow-ups. Always validate a retrospective alert against current state — a stale failure-count flag may mask a recovery. **Syntax-variant recurrence**: when false-positives persist through multiple context variants (digest-quoted mentions + plain-prose mentions) despite syntax-specific exemptions (e.g. #21694's digest-marker fix, task #21765 plain-prose mentions still recurred), apply per-instance cooldown-gating (48h mute after review) as tactical interim measure while structural prevention is designed — asymmetric cost scenario (many cheap false reviews drain budget faster than structural fix). **Implementation** (#21766): scan prior completed review tasks' descriptions via LIKE to find last close time; suppress re-flagging if <48h ago; signal-only candidates (parent/sibling/mention, no independent stale reason) get cooldown, but tasks with genuine stale-reasons bypass it since they're already structurally re-reviewable. Distinct from permanent exemptions: cooldown resets, allowing genuine stale conditions to eventually break through. **Escalation-to-structural**: when the same FP category recurs ≥5 consecutive times after a tactical fix (mute, exemption, cooldown) is deployed, do not iterate additional patches — escalate to a structural fix (detector mechanism redesign, architecture change, classification rule overhaul) in the same cycle instead. Cost of repeated tactical cycles (redeploy, re-review, re-debug) outweighs design debt for the upgrade; example: arc-blocked-review false-positive loop reached 5 consecutive re-flags post-48h-cooldown deployment, triggering immediate structural cooldown fix same cycle rather than another exemption patch.task #21805
**p-task-premise-verification** [2026-06-19] Tasks claiming to verify a feature/mechanism/safety guard should validate upfront: feature exists in runtime, claimed behavior matches implementation, supporting docs are current. Reject false-premise tasks at triage.
**p-live-state-precheck** [merged: p-work-already-done-precheck (6x) + p-blocked-workflow-diagnosis (4x), 2026-06-30 to 07-04] Before queuing/executing recurring/repair/maintenance/investigation work, or re-investigating a `blocked`/stuck task, check live state first rather than trusting task history or stale status. **General precheck**: run the relevant live-state CLI (`consolidate-memory check`, `sensor-health-report`), scan git/task history for the target fix or root-cause chain (e.g. #21165→#21169→#21178), verify config files for claimed gate/enable status, or query the external blocker's live state directly (PR closed? decision executed?) — also check recent commits for generic/system-level fixes that may already cover a feature-specific-looking gap (e.g. a sensor flagged missing `consecutive_failures` tracking was already fixed generically in `runSensors()`). Skip task creation, close as completed referencing the existing chain, or skip the investigation entirely if the work is already done — applies to single tasks, multi-wave repairs, recurring maintenance, and blocked-status review alike. **Blocked-workflow specific** — six checks before treating a blocked/stuck workflow as a defect: (1) validate against workflow design docs and sensor logic — "stuck" often reflects intentional gate-holds; (2) check config docs for drift against live implementation (e.g. CADENCE.md listing retired beats while dispatcher already moved on); (3) verify a claimed fix was actually deployed before concluding "no new signals" — undeployed fixes masquerade as policy-waiting (#20858); (4) consolidate 2+ blocked tasks sharing the same unresolved dependency into ONE escalation task; (5) key exclusion/allowlist sets on composite (template:state, beat:status), not bare state names, since reused names across workflows cause false-positive exclusions; (6) after a feature gate lifts, test the first live use rather than trusting the state-check alone — conversely, a sensor skipping 100% of candidates on a dormant source is expected, not failure; validate source status before reading zero-inflow as outage.
**p-standing-policy-gate-supersession** [2026-07-07, task #21494] Before treating a task's gate/sign-off requirement as current, verify it hasn't been cleared by standing policy (check skill CLI code/comments for directives) or prior explicit approval (check email history + MEMORY.md). Task descriptions lag behind mid-chain policy changes — trace authorization dates to distinguish stale framing from actual blockers.
**p-model-selection-strategy** [merged, deployed 2026-07-01, hardened 2026-07-04] Daily/weekly introspection + **follow-up task creation default to Sonnet**; reserve Opus only for genuine 3+ file/subsystem architectural ambiguity, open-ended investigation with no target file, or irreversible high-stakes calls (task #21143 audit: 4 follow-ups drifted to Opus with no criteria, all were bounded single-file fixes). Haiku floor: any `fix:`/`feat:`/`refactor:`/`chore:` touching TS/source must use sonnet minimum (Haiku ~5min timeout). **Open-weight routing**: GLM-5.2/Devstral-2512 via OpenRouter viable for bounded code tasks at 0.2–0.6% of Sonnet cost. Classifier LIVE via `--model auto`, deployed via CLAUDE.md instruction (fixed 0% adoption).
**p-policy-deprecation-atomicity** [merged] Policy deprecations and new data fields must touch three layers atomically: storage/docs, code/CLI, presentation. Missing any layer causes recurring failures or silent data gaps.
**p-dispatch-signal-freshness-gate** [2026-06-12] Tasks replying to external signals validate signal age at dispatch time. Mention >7 days old = close as completed no-op.
**p-claude-usage-quota-outage** [2026-05-14] Quota exhaustion → dispatch-gate `rate_limited` stop. Parse "resets HH:MM (Timezone)" from `stop_reason`; if current time ≥ reset time, auto-reset (rate-limit class only).
**p-external-side-effect-idempotency** [merged, extended] External-side-effect tasks (email/STX/x402/CLI post) self-verify before acting: check sent folder/tx history/receipt/messages in recent window, as FIRST step. Append-only ops dedup against in-memory AND persisted store. Dedup semantics: terminal states = "done, skip"; active states = "in progress, don't duplicate."
**p-review-task-confirmed-resolution-closure** [2026-07-05, task #21309] When a review/monitoring task confirms an external condition is resolved (blocked PR merged, bug fixed, workflow unblocked), task templates must instruct the agent to take terminal action (close blocked task, mark resolved) not just report the finding — otherwise the condition re-triggers at full cost next sensor cycle. Example: PR #638 blocked-task reviewed 3× same day because prior confirmations only reported "already resolved" without closing; fixed via sensor template instruction change directing closure on confirmed resolution.
**p-sensor-fire-rate-management** [merged 8x] Nine re-fire gates: (1) threshold sensors persist a result hash, re-fire only on improvement/cooldown; (2) static keys + short intervals flood — use date-scoped keys; (3) transient failures (429/timeout): check `getLastFailedTaskBySource` (4h) before queuing; (4) mixed reactive+proactive sensors need independent `claimSensorRun` entries; (5) scope source-key audits to state-change boundaries; (6) `already_queued` blocks should log + return `"ok"` not `"skip"`, encoding workflow state into the key (`source:state`); (7) integration sensors dedup by version (`source="sensor:<skill>:<repo>:<version>"`), use `json_extract()` not LIKE, verify local HEAD before re-queuing; (8) instance-ID dedup fails with N coexisting instances — scope to shared category (`source="retrospective:health-alert:TYPE"`); (9) exact-string exemption lists miss compound-identifier variants — use prefix-match or explicit suffix enumeration.
**p-overlapping-sensor-consolidation** [2026-07-04, task #21052] Multiple periodic tasks querying the same data window but producing complementary outputs (e.g., qualitative narrative + quantitative rubric) should consolidate into one task — prevents duplicate data-fetch overhead and meta-work doubling. Separate only if outputs have genuinely independent schedules/clients.
**p-shared-resource-multi-consumer-audit** [2026-07-06, task #21454] When investigating quota/cap exhaustion on shared input-side resources (API quotas, read-budgets), audit ALL consumers via grep + verify each importer has an active sensor/task path; calculate aggregate per-consumer share; apply fixes (widen high-frequency cadences, implement sub-budgets, guarantee critical-consumer minimums). Dormant importers don't contribute to consumption but can mask real patterns if not excluded.
**p-large-audit-aggregator-cli** [2026-05-16, validated Code Mode; extended 2026-07-05, 2026-07-09] CLI-wrapping reduces dispatch context cardinality. Any task reading ≥10 files: build CLI aggregator instead (e.g. `sensor-health-report` replaces 73 sensor.ts reads). Diagnostic review tasks discovering mid-cycle they lack required tooling should file the gap as a blocker-prerequisite rather than proceeding with degraded visibility — cost-review #21889 discovered no `arc tasks cost` CLI existed, filed #21891 to build it before next cycle. All consumers (sensors, audit tools, other code paths) must delegate to the aggregation CLI rather than re-implementing — duplication causes false positives (reporting stale state already fixed in consolidated version, e.g., arc-self-audit raw hook-state reads vs sensor-health-report's fixed identity-resolution) and maintenance divergence.
**p-dispatch-session-fork-limit** [merged: p-batch-research-fork-aware-inline-synthesis, 2026-06-18, extended 2026-07-06 task #21472] Dispatch sessions run as forked workers; Agent/Workflow subagent spawning succeeds once then fails with "Fork is not available inside a forked worker." Author reports directly in main loop using skill CLIs for data collection rather than fanning out. **Batch research application**: batches (5-50 items) constrained by fork-limits or cost (>$30 fan-out) should heuristic pre-filter → skip low-relevance → synthesize inline, avoiding nested agent spawning and cost while keeping complexity low.
**p-state-machine-safety** [merged multi-layer, 2026-07-01] Dedup'd creations need `autoAdvanceState` immediately or sensors re-fire. Feature flags gate both creation+evaluation layers. **Completion invariant**: non-terminal states never have `completed_at` set. **Terminal durability**: explicit terminals prevent repair tools reopening. **Resource fanout gates**: states creating tasks referencing external resources must verify availability before creation — noop-hold on 404 rather than blind fanout.
**p-noop-state-dead-predecessor-retry** [2026-07-05, task #21199] Noop-return states (awaiting external events/predecessor completion) silently eternal-wait if the predecessor task failed without retry. Fix: detect noop + predecessor task failed → retry the predecessor once (`:retry1` source), escalate if retry also fails. Prevents orphaned workflows stuck 2–3 months on dead predecessor.
**p-creation-timestamp-staleness-guard** [2026-07-01] State machines with deferred/multi-phase side effects must guard creation timestamp before executing downstream — prevents months-old content resurfacing. Guard at field-read, not just state-transition.
**p-state-machine-rename-data-migration** [extended 2026-07-04] When renaming state-machine state names, existing DB rows referencing old names silently noop. Include data migration in the same commit. Recovery: `arc-workflows transition` bypasses template validation to unblock rows. **CLI collision gotcha**: `arc-workflows`' `complete <id>` subcommand marks workflows fully terminal — when `allowed_transitions` names an event `"complete"` targeting an intermediate state, the CLI subcommand shadows it and leaves the workflow stuck; use `transition <id> <target_state>` for intermediate states instead (task #21099).
**p-resolver-mechanism-drain-verification** [merged, 2026-07-01] Resolver functions (clean-up/drain/purge) must run FIRST in multi-phase sensors, isolated in own try/catch — errors in other phases abort before resolver executes. Verify success via: (1) observable state-change delta matches expected scope, (2) timestamps reflect current cycle, (3) spot-check against external source.
**p-workflow-output-recompute-guard** [2026-06-30, extended] Templated workflows can complete output without advancing state (crash-recovery or stale external completion). On dispatch, validate output completion first before re-running compute; if complete, skip re-work and advance state directly.
**p-external-signal-dedup-versioning** [merged] Pagination creates invisible state-transition ranges. Dedup via completed-task + versioned source key (`pr-review:v1`) — allows per-commit re-review while preventing loops.
**p-architecture-review-discipline** [merged, extended 2026-07-05, 2026-07-07] Architecture review sensors gate on SHA diff — persist review SHA, skip if unchanged.
