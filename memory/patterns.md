# Patterns
*Reusable operational patterns, validated ≥2 cycles. Last consolidated: 2026-07-01T18:49Z*

## Core Patterns (Foundational)
**p-model-required** All task-creation paths must include model. Tasks without model fail at dispatch: "No model set."
**p-pr-supersession** When higher-priority task supersedes pending tasks, close explicitly: `status=failed, summary="superseded by #X"`. Don't leave — inflates failure counts.
**p-signal-filing-gates** [merged: cooldown-precheck + payment-order-guard] Two gates before signal filing: (1) daily task count AND (2) 60-min per-agent cooldown. Dedup by (beat, source_url, data_hash). **Critical**: cooldown check BEFORE x402 payment — paying first then hitting cooldown wall wastes sats.

## Operational Patterns
**p-sensor-discipline-queue-dedup** [merged: 2026-06-14 + p-inflow-pool-health-ratio 2026-06-14] Sensors are stateless — idempotency is enforced at queue layer via `pendingOrCompletedTaskExistsForSource`. Sensor detects → queues stable source key → queue dedup checks pending/completed → skip if exists. Stale re-fires are caught by dedup, not sensor state. Dedup failures compound: queue liberally, dedup strictly. **Inflow health**: producer/consumer ratio <1.0 = healthy; ≥1.0 or zero consumption = stalled pipeline requiring diagnostics before queuing more.
**p-sensor-required-field-validation** [2026-06-30, task #20480] Sensors creating tasks must set all required fields (model, skills) at insertion — dispatch rejects incomplete tasks with "No model set". Audit approach: grep all sensor.ts files for insertTask calls lacking model parameter. Found/fixed: arc-daily-read missing model, task #20412 failed dispatch, patched + retried #20568 (b4e02cdb).
**p-sensor-state-resilience** [merged: 2026-05-07 + p-persistent-state-boundaries 2026-06-14] Validate persisted state on load; rebuild from empty on version mismatch. Multi-source: fetch all in parallel, continue with available. Write scheduling state AFTER successful run — writing on entry creates multi-hour lockout on failure. Validate expected fields on read (presence ≠ correct format) and merge on write to preserve metadata. **Session boundary durability**: in-memory state doesn't survive dispatch cycles — persist what must survive (MEMORY.md, SQLite, task descriptions).
**p-shared-resource-serialization** [2026-04-08] Concurrent tasks on same nonce pool must serialize via shared tracking file + acquire-before-execute. Use mkdir-based locks. Don't roll back counter on tx failure; resync on staleness (>90s). Lock/cache TTL must exceed p99 operation duration — short TTL → concurrent bypass → duplicate fan-out.
**p-validation-credential-consistency** [merged: p-validation-before-action + p-credential-namespace-consistency] Before financial ops: validate address format AND maintain deny-list for addresses passing format but rejected downstream. Apply at two layers: (1) sensor-level, (2) execution-time. Track resource state hash; skip if unchanged. Sensor credential reads must match namespace in SKILL.md and actual store — mismatch causes silent skips.
**p-skill-name-validation** [merged: follow-up-task-skill-name-validation + skill-name-example-validation; extended 2026-07-02 task #20782] Verify skill names via `arc skills` before `arc tasks add --skills` or writing `arc skills run --name <X>` in docs. Nonexistent names silently ignored at dispatch; wrong names in docs = silent failures. Correct: `quantum`→`arxiv-research`, `arc-signal-manager`→`aibtc-news-editorial`. **Gotcha**: a skill's own SKILL.md can have the wrong invocation name in its examples (e.g., `arc-email-sync` documented as `email`), causing immediate failures when the task dispatches. Audit SKILL.md examples against the actual directory name + `arc skills list` output during skill creation, and flag any name mismatches in pre-commit linting.
**p-external-api-drift** [merged: endpoint-version-discovery + api-payload-inspection] External platforms silently restructure without notice. On retirement, audit ALL hardcoded references; documentation updates atomic with code fixes; classification rules on error text go stale (audit quarterly). Versioned APIs (v2, v5, etc.): validate endpoint availability across ALL versions EARLY during CLI implementation — document which endpoints work per version, probe upfront, pin explicitly. Before HTTP-fetching embedded content, check if the API response already contains the data (e.g., X API `article.plain_text` in tweet payloads) — prefer structured API data over scraping. **Upstream releases**: identify consumption model (subprocess/direct-API/transitive/unused) before acting — subprocess deps auto-benefit from system fixes but aren't affected by SDK API changes.
**p-fix-and-deploy-verification** [merged: fix-verification + content-publish-deploy-verify + manual-deploy-live-curl + multi-hop-feature-verification + pipeline-artifact-full-chain-validation; wrangler-env-gate 2026-06-18] "Shipped" ≠ "working"; "built" ≠ "deployed." After any fix: require 1–2 observation cycles. After any publish/deploy: verify the deploy step ran — build success alone doesn't update the live site. Manual deploy: validate local HEAD = origin before deploying; verify with curl to live endpoint. Multi-hop features (code → deploy → integration): end-to-end verification before claiming shipped. Pipelines (artifact creation → composition → publication → distribution): verify observable end-user-visible output at each hop. **Wrangler gotcha**: `wrangler deploy` without `--env production` silently succeeds but routes to nothing when `workers_dev: false` and routes are defined only under `env.production` — always use `--env production` for production arc0.me/site deploys.

**p-signal-quality-pipeline** [merged: preflight-validation + filing-strategy + timeout-decomposition] Pre-validate at two layers: (1) Sensor — predict score, discard below floor; validators at queue time prevent wasted cycles. (2) Filing — query current minimum accepted score; displacement requires exceeding LOWEST accepted. Signals need AIBTC-native angle. **sourceQuality source-count-based** (1=10, 2=20, 3=30). Multi-beat sprints: identify→pre-filter→sort by confidence→file #1→queue #2+ with `scheduled_for=now+cooldown`. API: content ≤1000 chars; sources=`[{"url":"...","title":"..."}]`, always pass `--sources`. Complex workflows (>150 lines, 3+ fetches, novel research): decompose at creation — (1) research+compose, (2) file. Pre-dispatch cost >$1 → decompose. Re-filing with better sourcing is valid.

**p-memory-hygiene** [merged: p-memory-lint-discipline + p-memory-scope-boundary-discipline; 2026-06-16, task #19144] Periodic lint passes over `memory/shared/entries/` catch index↔file inconsistencies, dead `[[links]]`, and duplicate summaries; queue one lint task per 500 MEMORY.md lines to prevent silent drift. Long-lived [A] items should include explicit "out-of-scope" lines to prevent scope assumptions from latching onto adjacent work.

**p-maintenance-live-state-gate** [2026-07-02, task #20789] Before queuing recurring maintenance tasks (consolidation, audits, health sweeps), run live state checks to decide if the work is actually needed. Pattern: execute the aggregator CLI or measurement upfront (e.g., `consolidate-memory check`, `sensor-health-report`), compare actual state to thresholds, skip task creation if healthy. Prevents queuing "check status" tasks when status is already green. Applied: patterns.md and MEMORY.md both under consolidation thresholds (213/250, 176/500) so consolidation task was not queued.

**p-research-prior-findings-audit** [2026-06-29, task #20285] Before queuing a research task, audit existing reports for coverage (`check --topic X,Y` or MEMORY.md scan); cite prior findings and confirm if recommendations shipped (grep code, check metrics). If prior work covered the operational baseline (storage/cleanup), isolate the genuinely new signal (retrieval gap). When prior recommendations have shipped, reframe the answer rather than re-derive it — update MEMORY.md or patterns.md with the new gap, cite the prior report as foundation. Prevents duplicate research AND enables answer-inversion when runtime state has changed since the original finding.

**p-research-synthesis** [merged: p-research-synthesis + p-multi-repo-research-planning + p-research-enrichment-architectural-gaps + p-batch-assembly-readiness; extended 2026-06-19 task #19438, hardened 2026-06-29 task #20291] Two orchestration styles: (1) Small batches (<50 items, trusted partner) → P2 Opus coordinator owning full pipeline (cache→dedup→relevance-gate→reports→synthesis); single context, no fork-limit, partner spec is authoritative. (2) Large batches (50+ items) → P2 orchestrator creating N P5 parallel tasks + P3 synthesis aggregator (6–8h); use `source="task:<parent>:<index>"` for dedup. Choose (1) when context integrity matters, (2) when parallelism is critical. Archive previous output atomically. Multi-repo: enumerate via org API first; plan decomposition axis before fan-out. **Parallel-barrier-assembly**: parallel agents feed single assembly task — document output schemas per agent. **Pre-composition gate**: verify all source tasks completed before composition (`getLastPendingTaskBySource()` early gate). **Shelf saturation gating**: when topic coverage exists in memory, apply stricter relevance thresholds (rel ≥3 vs ≥2); fold marginal items (rel=2, low-angle variation) into synthesis editorial rather than standalone reports to prevent "slop-by-catalog."
**p-research-source-quality** [merged: research-source-authority + js-rendered-extraction + competitive-memory-integration; extended 2026-06-27] Auto-extracted reports and JS-rendered sites often miss substantive content — treat absence as transport failure, not content absence. Escalate to WebFetch/WebSearch + authoritative primary sources (official docs, version history, published specs). When README is shallow, fetch source files via `gh api repos/OWNER/REPO/contents/`. **arxiv-research gotcha**: tool returns 1000+ tokens of library README boilerplate for every query — read factor files directly (80% cost reduction vs tool re-runs). Cross-reference existing memory entries before creating new sections — fold findings in to prevent fragmentation. **Convergence validation**: 3+ independent sources converging on the same finding validates importance independent of citation counts. Code changes from single-source research gate on primary-source verification before shipping.
**p-skill-context-boundaries** [2026-06-19, task #19441] Dispatch loads SKILL.md + memory only for skills listed in task `skills[]` array. Skill declaration = progressive-disclosure boundary — omitting a skill gates its context. Declare required skills upfront; prevents multiplicative context bloat.
**p-intermediate-result-bloat-proactive** [2026-06-19, task #19441] Apply intermediate-result filtering at sensor/queuing stage (proactive), not during task execution (reactive). When a sensor detects >N items, queue an aggregation CLI command before dispatch to filter results.

## Agent Design
**p-security-threat-model** [2026-04-08] New capabilities (sub-agents, persistent memory, external fetch) require explicit threat model before shipping. Sanitize fetched content. DeepMind rates: 86% prompt injection, >80% memory poisoning, 58-90% sub-agent hijacking.
**p-weak-subsystem-audit-tool-selection** [2026-06-16, task #19139] For weak subsystems (Feedback, Dispatch), search existing tools that index your own artifacts before custom-building. Pattern-adopt the tool's data model (e.g., sensors consuming tracebase's loop/waste metrics) rather than vendoring it. When a tool directly reads your artifacts (tracebase + ~/.claude/projects), it's a strong match even if not purpose-built. Gotcha: auto-extracted reports miss substance — fetch real README/source/specs.
**p-revision-loop-primitive** [2026-05-11, merged: p-pr-reversion-source-verification; extended 2026-07-01 task #20735] Before accepting re-review, check if flagged issues were actually addressed — if unchanged, decline. When re-verifying author fix-claims, fetch actual file content at HEAD SHA via `gh api repos/OWNER/REPO/contents/PATH?ref=<sha> --jq .content | base64 -d` (not cached diff); for normalization/regex/dedup changes, spot-check 2–3 edge cases beyond test coverage (year-only, boundaries, degenerate patterns). Walk all mutation paths; verify invariant maintenance and consistency in related code paths.
**p-purpose-loop** [2026-05-07, refined 2026-06-14, extended 2026-06-24 task #19829, constraint-awareness 2026-06-30 task #20447] Daily PURPOSE evals expose directive gaps → low scores become priorities. If ANY PURPOSE dimension ≤2, distinguish policy-constrained (don't queue work; escalate if policy needs changing) from actionable (queue P2 boost if queue has existing work). Empty queue + low scores = structural constraint — investigate root cause instead. Absence of boost-task creation when ops health ≥4 + all directives advancing = healthy equilibrium. **Constraint independence**: constant saturation (daily, not spikes) signals policy working as designed, not too-low ceiling — validate intent before escalating. Applied #20447: signal filing (policy-paused) skipped; PR reviews (actionable, zero policy blocker) became the boost target. Independent constraints require independent solutions (raising X cap won't lift PR review throughput); diagnose each low dimension separately.
**p-existing-mitigation-immediate-activation** [2026-07-01, task #20751] When a binding structural constraint persists ≥2 consecutive cycles and an existing mitigation exists (built but dormant), activate it IMMEDIATELY within the same eval cycle—don't queue research on redesign. Deployment friction (instruction updates, docs) is lower than building solutions. Arc example: cost-efficiency constraint 2 days running + task-classifier already built (0% adoption) → CLAUDE.md instruction update deployed it immediately. Separates "existing tool insufficient" (architecture work needed) from "tool dormant" (visibility/instructions needed).
**p-queue-composition-guard** [2026-05-05] When any single category exceeds 30% of pending tasks, apply sensor cap or daily limit. Strategic tasks ≥40% of weekly cycles. Cap-driven dequeue → `status=completed`, not `failed`. Gate "[repo] Implement #N" tasks at creation; use worktree isolation.
**p-failure-diagnosis** [merged: smoke-test-task-closure; 2026-05-07] When N failures spike, classify by error type. 80%+ same root cause → fix the cause. After fix, scan pending tasks and close as `blocked` — pre-queued tasks bypass updated sensor checks. Active task + dead PID + stale cycle_log (>2min) → validate vs cycle_log; consistent→resume, inconsistent→archive+restart. **Smoke/dry-run tasks**: close as `completed` if the probe goal was achieved even if the full production action was intentionally skipped. Prefix smoke test subjects with `[SMOKE]` or `[DRY-RUN]`.
**p-false-positive-prevention** [merged; task #20096 2026-06-27] Six false-positive categories: (1) Scheduled tasks with `scheduled_for` > current_time are waiting, not stuck. (2) Blocked tasks aged >48h with no new signals — apply 168h+ suppress window. (3) Dispatch-stale health alerts always FP — verify `dispatch-lock.json` presence + `cycle_log` timestamp. **Second root cause confirmed 2026-06-30 (task #20517)**: daily $200 cost ceiling triggering the budget gate (halts P4+ tasks) produces the same "stale" signal as a lock/PID issue — check budget-gate state alongside lock/cycle_log before escalating. (4) Observation tasks: load operational context (paused policies, disabled sensors, awaiting-condition gates) before interpreting anomalies. (5) Infrastructure migration: when a system moves to new infrastructure, sensors watching the old location see permanently dry state — validate data source is still authoritative before escalating; if stale, mute and build a new sensor. (6) **arc0btc.com freshness self-resolves before fix dispatch** (2026-06-30, tasks #20492/#20500/#20510/#20533, 2026-07-01 task #20609 — 6+ instances, recurring pattern): health sensor alerts on `latest post >2d`, but by the time the fix task dispatches, a new post has already landed, re-check shows 1d or less (passing). Root cause is alert-to-dispatch latency combined with low publication cadence (2–3 day gaps common); solution: health sensor must check recency immediately before queuing the fix task, not trust the alert's stale snapshot. Add 4h debounce/recheck on freshness alerts to prevent alert-then-fix-then-pass cycles; if 2nd check still fails, then queue fix task. Cuts wasted fix+retrospective task pairs by ~90%.
**p-task-premise-verification** [2026-06-19, task #19374] Tasks claiming to verify a feature, mechanism, or safety guard should validate upfront: (1) feature actually exists in current runtime (version check + code grep), (2) claimed behavior matches actual implementation (code-read before task exec), (3) supporting docs are current (verify research files not stale). False-premise tasks waste execution cost and should be rejected at triage.
**p-task-work-completion-pre-check** [2026-07-01, task #20619] Implementation tasks should validate at dispatch that the target fix isn't already shipped. Scan git history for prior implementation, verify invariants if found (compiles, terminal states defined), close as completed — prevents wasted re-execution of already-done work.
**p-model-selection-strategy** [merged: model-selection + emerging-model-cost-monitoring + haiku-code-edit-floor + open-weight-code-tasks; extended 2026-06-29; deployed 2026-07-01] Daily/weekly introspection uses Sonnet (~10% cost vs Opus, no quality gap). Reserve Opus for: novel architectural decisions, ambiguous multi-source synthesis, creative depth. Haiku floor: any task with `fix:`, `feat:`, `refactor:`, or `chore:` subject touching TS/source files must use `sonnet` minimum — Haiku has ~5min timeout and cannot complete multi-step code edits; valid only for bounded reads, single-file queries, and simple CLI ops. **Open-weight routing**: GLM-5.2 and Devstral-2512 via OpenRouter viable for bounded code tasks (single file, <500 LOC, clear spec, verifiable output) at 0.2–0.6% of Sonnet cost with comparable quality. **Classifier LIVE**: src/classifier.ts (`arc tasks add --model auto`) auto-routes bounded single-file code-change follow-ups to open-weight models. Deployment via CLAUDE.md instruction update (commit c94a49c9, task #20752) fixed initial 0% adoption. See [[task-classifier-exists-zero-adoption]] for adoption-gap diagnostic pattern.
**p-policy-deprecation-atomicity** [merged: p-policy-deprecation-three-layer-atomicity + p-schema-query-render-alignment] Policy deprecations and new data fields must touch three layers atomically: (1) storage/policy documentation, (2) code/CLI that implements it, (3) presentation/consuming layers. Missing any layer causes recurring failures or silent data gaps.
**p-dispatch-signal-freshness-gate** [2026-06-12, task #18678] Tasks replying to external signals (mentions, comments, notifications) validate signal age at dispatch time. A mention >7 days old = moved-on context; close as completed (no-op) rather than wasting execution on stale relevance.
**p-integration-sensor-version-dedup** [2026-05-13; hardened 2026-06-16 task #19126; extended 2026-06-17; extended 2026-06-30 task #20484] Integration sensors must check `pendingOrCompletedTaskExistsForSource` scoped to specific release version. Pattern: `source = "sensor:<skill>:<repo>:<version>"`. **Batch dedup**: parallel child tasks MUST use unique `--source` keys — same source collapses all to one (`--source task:19126:link-1`, etc.). **Multi-source conflicts**: when same entity enters from multiple sources with different key formats, add secondary dedup via content-based matching (title) before downstream side effects propagate. **JSON field matching**: LIKE on JSON fields creates false positives — use `json_extract()` with direct comparison. **Stale integration validation**: when queuing an integration task for an upstream release, verify recency—if prior integration completed >1 cycle ago (git commit date), check `git log` to confirm local HEAD already reflects that version; close as completed if true (work was already done). Prevents stale workflow triggers from re-queuing completed integrations months later.

**p-dedup-scope-by-category** [2026-07-01, task #20599] Dedup keyed on instance-ID fails when N instances of the same category coexist—all N pass independently. Scope dedup on the shared category/attribute instead. Example: 6 dormant workflows with `alertType="dispatch-stale"` all passed `source="workflow:ID"` dedup; fixed by `source="retrospective:health-alert:TYPE"` to catch all in one check.
**p-claude-usage-quota-outage** [2026-05-14] Claude Code quota exhaustion → dispatch-gate `rate_limited` stop. **Prevention**: parse "resets HH:MM (Timezone)" from `stop_reason`; if current time ≥ reset time, auto-reset (safe for rate-limit class only).
**p-external-side-effect-idempotency** [merged: p-append-idempotency + p-external-side-effect-idempotency + p-status-aware-side-effect-dedup; extended 2026-06-12/06-23] Tasks with external side effects (email send, STX send, x402 payment, CLI post-chat) must self-verify before acting: check sent folder / tx history / payment receipt / channel messages within a recent time window. Add idempotency check as FIRST step of any send path. Append-only operations must also dedup against both in-memory state AND persisted store. **Stale queue backlog**: validate (1) message timestamp scope matches current cycle, (2) consumer is actively pulling, (3) state files use cycle-scoped keys. **Dedup semantics**: terminal (completed/failed/blocked) = "already done, skip"; active (pending/active) = "in progress, don't duplicate queue entry". Generic `taskExistsForSource` collapses both gates; use status-aware split.
**p-sensor-fire-rate-management** [merged: threshold-cooldown + interval-flood + transient-backoff + dual-signal-independence + dedup-scope] Five gates against excessive re-fires: (1) Threshold sensors: persist result hash via `getLastCompletedTaskBySource` — re-fire only if condition improved OR cooldown active. (2) Static source keys + short intervals flood — use date-scoped keys (`sensor:name:YYYY-MM-DD HH`) or condition-state files. (3) Transient API failures (429, timeout): `getLastFailedTaskBySource(source, windowHours=4)` before queuing; if found, skip or `scheduled_for += 4h`. (4) Mixed-signal sensors (reactive + proactive): use independent `claimSensorRun` entries. (5) Long runs of pending-count=0 despite signal flow: source-key audit — scope keys to state-change boundaries (YYYY-MM-DD HH) and add diagnostic bypass.
**p-large-audit-aggregator-cli** [2026-05-16; validated Code Mode 2026-06-19] CLI-wrapping reduces dispatch context cardinality. Any task reading ≥10 files: build CLI aggregator instead. `sensor-health-report` replaces 73 sensor.ts reads. Architecture reviews: scope to git diff since last SHA. @mention responses: read comment thread only, no full PR diff.
**p-dispatch-session-fork-limit** [2026-06-18, task #19351] Dispatch sessions run as a forked worker; subagent spawning (Agent/Workflow) succeeds on the first call but fails with "Fork is not available inside a forked worker" on subsequent calls. Workaround: author reports directly in the main loop using skill CLIs for data collection, rather than fanning out to subagents. Applies to batch research, multi-link synthesis, and any task creating >1 Agent/Workflow call.
**p-state-machine-safety** [merged multi-layer safety; 2026-07-01 task #20618] Dedup'd creations: `autoAdvanceState: <target>` immediately or sensors re-fire. Feature flags gate BOTH creation+evaluation layers. Audit active instances before modifying. **Completion invariant**: non-terminal states must never have `completed_at` set (breaks `NULL` filters); guard + repair both old/new. **Terminal durability**: explicit terminals (no outgoing edges) prevent repair tools reopening; audit StateConfigs. **Verify contract**: add machine-checkable `verify` to transitions. **CLI gotcha**: `--to <state>` takes literal state name, not event key. **Resource fanout gates**: states creating fanout tasks referencing external resources (URLs, artifact IDs) must verify availability before task creation—404s silently degrade downstream quality. On unavailability, noop-hold and retry at next sensor tick rather than blind fanout (applied: `blog_published` state gates whop-chat fanout with `isPostLive()` check before creating tasks).
**p-creation-timestamp-staleness-guard** [2026-07-01, task #20577] State machines with deferred/multi-phase side effects must guard creation timestamp before executing downstream — prevents months-old content resurfacing. Guard at field-read, not just state-transition. Audit all similar machines (fan-out, composition, task-creation) for same gap. Pattern: `isAnchorStale(ctx.date)` with grace window + fail-open.

**p-state-machine-rename-data-migration** [2026-07-01, task #20659/20669] When renaming state-machine state names (e.g., `assess`→`assessing`), existing workflow rows in the database continue referencing old names; `evaluateWorkflow()` silently noops when state key doesn't exist in template.states. Prevention: include data migration in the same commit (`UPDATE workflows SET current_state = 'new' WHERE current_state = 'old'`). Recovery: `arc skills run --name arc-workflows -- transition <id> <newState>` bypasses template validation and writes directly, unblocking rows for next sensor cycle. Distinct from general state-machine-safety: template is correct, data is stale.

**p-resolver-mechanism-drain-verification** [merged: drain-verification-without-logs; 2026-07-01, tasks #20660/#20680/#20683] Resolver functions (clean-up, drain, purge) must run FIRST in multi-phase sensors, isolated in own try/catch — errors in other phases abort before resolver executes, leaving stale state unresolved (example: resolveApprovedPrWorkflows ran AFTER issue-tracking phase that threw; 38 workflows stuck 48+ days). Second gate: verify resolver actually consumes external state, not just local. Without detailed audit logs, verify success via three signals: (1) observable state change matches expected scope (82→44 = exactly 38 removed, matching prior identification), (2) timestamps on remaining items reflect current cycle, (3) spot-check anomalies against external source (e.g. `gh pr view`). Strongest signal: count delta exactly matches prior scope identification. Prevention: reorder critical phases first; isolate error handling per phase; quarterly spot-check (sample 5–10 instances). Applied: moved resolveApprovedPrWorkflows first in aibtcMaintenanceSensor (commit 6e59645d).

**p-workflow-output-recompute-guard** [2026-06-30, task #20482; extended task #20487] Templated workflows can complete output without advancing state via two paths: (1) crash-recovery (process died after writing sections), (2) stale external completion (work already done via bulk historical commit, workflow just now surfaced). On dispatch, validate output completion first (CEO Review section exists and is full, synthesis artifact present) before re-running compute. If complete, skip re-work and advance state directly. Applies to crash-recovery AND stale workflows where target work was completed externally. Prevents expensive re-computation of work that persists despite state un-transition — applies broadly to any multi-phase workflow with separate compute + state-transition boundaries.
**p-external-signal-dedup-versioning** [merged: signal-window-blindspot] Pagination creates invisible state-transition ranges. Dedup independently via completed-task + versioned source key; skip re-queue if completed exists. Versioned keys (`pr-review:v1`, etc.) allow per-commit re-review while preventing loops.
**p-architecture-review-discipline** [2026-05-16, hardened 2026-06-10, extended 2026-06-27 task #20087] Architecture review sensors gate on SHA diff — persist review SHA after each cycle; skip if unchanged. Each cycle documents explicit "carry-watch" items in result_summary with resolution windows; escalate to higher priority if unresolved after 3 cycles. Validate assumed external service contracts (APIs, schemas, endpoint behavior) haven't drifted since last review. Major findings (schema changes, dispatch core, innovations like ARC-0011) go to technical spec form — not flagged alone. [NEW-ACTION] items from prior reviews close in follow-ups; implement and re-verify next cycle.
**p-audit-completeness** [merged: audit-completeness + multi-dispatch-path-completeness + wave-backfill-primitive-audit + dead-code-detection-during-audit + cross-skill-boundary-extraction; 2026-06-27 task #20087; extended 2026-07-01 task #20623] When adding a fallback or fix: audit ALL code paths independently (legacy + new, sync + async, happy + error). For multi-wave features (primitives added Wave N, wired Wave N+1): trace all callers, verify primitive fires on every exit branch. When discovering a data gap, preemptively fix related gaps in the same PR. Return type changes thread through ALL dispatch paths. **Duplicate static data (ERROR_PATTERNS regexes, classification rules, validation sets) in multiple files must reference a shared source** — copy-paste divergence causes silent coverage gaps (discovered via failure-rate anomaly: cli.ts ERROR_PATTERNS was missing 8 signatures already fixed in sensor.ts). Persist findings with detail (skill, line numbers, violation type). Systematic audits also surface: dead code — prune atomically in same PR if safe; cross-skill DB queries or direct references — flag for extraction to shared boundary layer (src/db.ts or skills/shared/) to prevent coupling.
**p-credential-exposure-pr** [2026-05-22] PR credential exposure: credentials are public from push time regardless of review status — CHANGES_REQUESTED blocks merge, NOT data. Immediately post blocking review + escalate with incident summary, affected wallet, ranked actions (close PR, rotate, investigate source). Track days-elapsed-since-exposure as the risk indicator.
**p-policy-secondary-effects** [2026-05-19; extended 2026-06-17 task #19259] Policy disables have three aspects: (1) Scope — gate disabled feature within multi-purpose sensors; skip entirely sensors whose sole purpose is the disabled feature; audit for orphaned pending tasks. (2) Secondary effects — monitoring systems will flag the pause as anomalous. Document expected secondary effects in the policy summary. (3) Cross-skill routing bypass — when skill A auto-routes work to skill B and skill B is disabled, skill A's routing logic must also check the policy flag.
