# Patterns
*Reusable operational patterns, validated ≥2 cycles. Last consolidated: 2026-08-17 (task #26431, marginal-overflow fold-in)*

## Core Patterns (Foundational)

**p-task-closure-discipline** Four rules: (1) supersession — close redundant pending tasks explicitly (`status=failed, summary="superseded by #X"`) rather than letting them fail on their own; (2) confirmed-resolution — when a review confirms an external condition resolved, take terminal action same cycle, don't just report it; well-established self-resolving TTL patterns (11+ confirmed recoveries, e.g. oauth-expiring) can skip follow-up filing and close directly after state verification; (3) terminal immutability — completed/failed/blocked states must reject re-closure (guard at CLI layer, `cmdTasksClose` exits 1 on terminal tasks); (4) verify a claimed side effect actually executed before closing with a summary claiming it did — don't trust "recurring pattern" memory-citations as sole justification without literal command output.

**p-live-state-precheck** Before queuing/executing recurring, repair, or re-investigation work, or before treating a blocked/stuck task as a defect, verify live state first (run the relevant status CLI, grep code, query config) rather than trusting task history or stale prose. Applies broadly: decision-blocked → email history; PR-merge-blocked → `gh pr view`; resource/config-blocked → live endpoint query; auto-generated upgrade tasks → check if already shipped upstream. Distinguish zero-inflow (dormant source, expected) from all-gated (signals generated but filtered by miscalibrated guards, needs tuning) — a 100% skip-rate across 2+ windows signals guard miscalibration, not dormancy. Cross-lane/cross-channel defer signals must be verified against actual output, not just activity-log ticks.

**p-false-positive-prevention** Recurring FP causes: `scheduled_for` omitted runs immediately (must pass explicitly for deferred tasks); dispatch-stale alerts must check PID liveness before trusting timestamp age; guard-skip conditions (budget exhaustion, rate-limit, rejection) should yield sensor `"skip"` not `"error"` — misclassification inflates failure counters into false escalations; check `arc tasks --status blocked` for an existing matching gate before filing a duplicate escalation; prose-text references to a blocked task ID (digest quotes, synthesis mentions) are a weak signal — verify actual state change, not text mentions. When the same FP category recurs ≥5 times after tactical patches, escalate to a structural fix instead of iterating. Benign early-close idle-timing skew (`completed_at` ordering) is common and structural, never tampering — verify via attempt_count/cycle_log row-count before escalating as a security incident. Skills with built-in consolidation logic (arc-skill-manager queuing memory compaction) can appear "hungry" on queue metrics when they're correctly self-gating — validate whether an apparent spike is genuine unbounded hunger or a legitimate self-limiting queue operation before escalating. [merged: p-sensor-stale-state-escalation, 2026-08-14 #26184] Recurring sensors producing unchanged output (hash-tracked) should escalate to whoabuddy with a time-gated cooldown after N consecutive unchanged cycles (e.g. N=2 ~14d) rather than silent re-queue loops; document threshold/cooldown mechanics in SKILL.md to prevent indefinite duplicate-task generation.

**p-line-count-threshold-vs-byte-size-consolidation-gap** `wc -l` is the wrong proxy for context-load cost — merging duplicates into fewer, longer lines satisfies a line-count gate without shrinking byte/token cost, so the threshold re-fires within days. Measure `wc -c` against the dispatch context budget (CLAUDE.md's 40-50k tokens) instead; when consolidating, prefer moving fully-superseded detail to `memory/archive/` or per-topic shared-entry files over re-merging into denser single lines.

**p-memory-lifecycle** Self-referential files (MEMORY.md, patterns.md) need periodic consolidation: (1) merge near-duplicate entries with `[merged: ...]` lineage tags, not word-duplication; (2) prose-density pass — convert verbose paragraphs into compound numbered structures, cuts chars with near-zero semantic loss; (3) marginal overflow (<5 lines over threshold) — fold new same-day entries into their closest existing pattern as numbered variants (`p-name-1`, `p-name-2`) rather than a full rewrite. Binding constraint is char count, not line count (MEMORY.md dispatch fails silently ≥24.4KB). Monolithic-consolidation risk is *semantic scope*, not raw line count — narrow-scope passes (dedup, prose-tighten) stay one-pass even at 200+ lines; structural redesigns (reclassify categories) should decompose per-section. Spot-check 2-3 merged entries for content preservation before committing; snapshot to `memory/archive/` first. Pre-consolidation step: grep all inbound wikilinks/backtick-quoted citations and validate each cites an actual entry — divergence (missing entry, misnamed cite) gets handled separately from structural rewrites to prevent silent loss of actively-referenced content. [merged: p-consolidation-stale-reference-refresh] MEMORY.md `[A]` active items and audit findings frequently reference external states that have since progressed — cross-reference each entry against git history, task completion status, and decision status (email/task-table) rather than trusting the tag; a resolved task can still carry unfinished obligations, check the full result_summary not just status; update stale entries in the same cycle to prevent re-investigation loops.

**p-model-selection-strategy** Follow-up task creation defaults to Sonnet; reserve Opus only for genuine 3+ file/subsystem architectural ambiguity, open-ended investigation with no target file, or irreversible high-stakes calls — bounded single-file fixes are never Opus regardless of priority. Haiku floor: any code-touching task or open-ended retrospective/pattern-extraction writing hits Haiku's ~5min timeout — use Sonnet minimum. `--model auto` (open-weight routing via classifier) is for bounded, single-file, mechanical follow-ups only — never from sensors, never for judgment calls.

**p-security-threat-model** New capabilities (sub-agents, persistent memory, external fetch) require an explicit threat model before shipping; sanitize fetched content (CSS-hidden text, hidden elements). Agent-controlled gateway/endpoint overrides must validate via allowlist, not denylist. Credential exposure in a PR is public from push time regardless of review status — post blocking review + escalate immediately. Verify claimed security mechanisms (sandboxing, isolation) against actual runtime config, not documentation — disabled mechanisms with a compensating layer are fine, disabled with no fallback is exposure. When integrating external security research, identify its axis (attack-catalog/defense-posture/incident-response), layer against your architecture, and state what it does/doesn't close — inherited defenses from a foundational layer don't eliminate custom-code vulnerabilities.

**p-security-guard-single-point-integration** [2026-08-18, task #26535] When adding guards to production paths, locate the canonical single entry point (e.g., `sendReply()` for all X replies) rather than scattering checks across multiple sites — makes guard placement, testing, monitoring, and maintenance straightforward. Validate key invariants before guard placement (e.g., confirm AGENT.md never loads into orchestrator) to prevent building on false assumptions; enumerate all actual send surfaces and measure whether consolidation overhead (shared hook, new abstraction) exceeds per-site duplication cost. Graduated rollout (critical path first, explicit follow-ups for remaining surfaces) reduces blast radius of oversight and allows iterative learning.

**p-graduated-security-hardening** [2026-08-18, task #26539 follow-up from #26535] Implement security controls for the highest-exposure surface first (validate in production), then file explicit follow-ups for remaining surfaces ranked by exposure — reduces coverage risk and allows learning from the critical case before extending. Gap-tracking (open follow-up tasks, not silent incompleteness) prevents stale unguarded surfaces from accumulating undetected.

**p-security-research-deployment-surface-mapping** [2026-08-12, task #25875] When importing external security research (threat models, vulnerability chains, attack taxonomies), ground the attack surface against actual deployment — a finding on cloud-encrypted-at-rest/plaintext-in-reasoning applies differently if you persist reasoning locally + decrypt credentials in-process (same-process leak vs. cross-account). Document which architectural features ARE exposed vs. mitigated vs. require fixes; validate this isn't just the paper's example re-instantiated but a genuine risk for your infrastructure. Example: Arc session transcripts persist reasoning locally, getCredential decrypts secrets into dispatch context — this re-creates the encrypted-plaintext leak without cloud infrastructure.

**p-rate-limit-budget-discipline** Pre-validate capacity before queuing; overflow → `blocked` with `scheduled_for` at reset, not `failed`. X: DAILY_TWEET_CAP=6 total/day, resets UTC midnight, root-post budget separate from reply continuations. Low-cap situations compress multi-part content into fewer slots rather than deferring. Deferred operations still burn LLM dispatch tokens even when the side effect is refused — track cost/deferred separately from cost/completed, and mark tasks `blocked` at gate-time to surface contention before burning tokens. Gates that fail-open on a time condition (no deferral-memory) let all deferred work fire simultaneously at a shared reset boundary (e.g. UTC midnight) — track deferral attempts or time-bound readiness to a short window. A resource exhaustion on one lane can write a shared flag suppressing ALL lanes silently for extended periods — surface cascade-width to decision-makers as one incident, not N task failures. When a queued side-effect reaches execution against an already-escalated gate, close `completed` with a void summary, not `failed`/requeue.

**p-state-machine-safety** Dedup'd task creations need `autoAdvanceState` immediately or sensors re-fire. Non-terminal states never set `completed_at`. Noop-return states awaiting a predecessor silently eternal-wait if the predecessor failed without retry — detect noop+failed-predecessor, retry once, escalate on second failure. Transition CLIs must validate the target argument names an actual state (not an event name) and fail loudly on mismatch — verify actual resulting state via re-query, don't trust the transitions-map. Cleanup/monitoring logic auto-resolving workflows must check ALL states instances can reach, not just the initial one — dispatch-driven intermediate transitions (e.g. `triggered→acknowledging`) are invisible to cleanup scoped only to the initial state.

## Operational Patterns

**p-sensor-fire-rate-management** Sensors are stateless — idempotency lives at the queue layer (`pendingOrCompletedTaskExistsForSource`); queue liberally, dedup strictly. Sensors creating tasks must set all required fields (model, skills) at insertion. Unbounded-candidate producers need a per-run filing cap or score-ordered top-N — volume, not model-routing, is usually the real cost driver when cost-per-task rises (diagnose via `arc tasks cost --days N --top 10` before retuning model tiers). Threshold/regeneration sensors should persist a result hash and skip re-fire when output is unchanged. Infrastructure-staleness sensors should pair low-frequency cadence with high thresholds; maintain a separate `last_progress_at` distinct from `updated_at` so bulk repairs don't mask eternal-wait states. Monorepo release sensors must filter at ingestion (package-name prefix) to avoid assessing unrelated sub-packages. Meta-work ratio >40% of daily completions or >$50/day is a signal to audit consolidation cadence, not accept as structural.

**p-external-api-drift** External platforms restructure without notice — audit hardcoded references on retirement, pin versioned-API endpoints explicitly. Prefer structured API data over scraping. Before investigating an issue on an external platform, confirm the claimed mechanism still exists (live docs/changelog) — feature retirement invalidates the investigation premise. Undocumented field-length limits should be validated at integration time and documented in SKILL.md. APIs billing per-request often support unlimited fields at no marginal cost — request the full field set upfront. Platforms with global-namespace auto-derived identifiers (slugs, handles) only reveal collisions at claim-time — expose a post-discovery correction flag rather than DB surgery. Retiring an endpoint via 410 Gone (vs 404/200) gives correct HTTP semantics for pollers.

**p-fix-and-deploy-verification** "Shipped" ≠ "working"; "built" ≠ "deployed." After any fix, require 1-2 observation cycles; after any deploy, verify via curl against the live endpoint, not just exit code — deploy tools bundle on-disk filesystem state (untracked files included), so `git status -s` before deploying to catch stray/reverted artifacts. Regeneration tasks should verify byte-for-byte idempotency to HEAD AND validate live deployment independently. Multi-step pipelines hitting transient failures (segfault/OOM/network) should recover via the skill's targeted resume CLI, not a full pipeline re-run, to avoid double-creating immutable artifacts (duplicate posts, resent emails).

**p-research-synthesis** Before queuing research, audit existing reports for coverage — cite/reframe prior findings rather than re-deriving. Auto-extracted/JS-rendered sources often yield boilerplate-only scrapes (high repetition, low domain-keyword density) — detect before writing and escalate to WebFetch/primary sources upfront, not mid-report. Convergence of 3+ independent sources validates architectural importance; a single external source confirming an existing internal design is a terminal validation finding (consolidate memory, no implementation needed), distinct from discovery (queue work). Verify claims against live code at draft-start, not just at research-time — codebases drift, and a bug fixed post-research invalidates the article's premise. Large-batch (50+) triage runs three gates: (1) **mechanical link-caching before scoring** (catches hypothesis-errors & preview divergence, not just link fetchability); (2) cluster-under-cap (merge adjacent angles into one task); (3) three pre-decline verification checks: categorical prescreen, primary-source verification, AND **concrete shipped-artifact exit condition** (each topic must state a checkable hypothesis + exit condition tied to an actual shipped artifact — feature, CLI, fix, integration — not just prose/blog/writeup). This prevents zero-conversion research bursts by filtering at queue-time. Exit-condition discipline ≥2 consecutive high-triage-to-low-dispatch: require artifact exit, not prose exit. **Preview-text divergence is an independent gate trigger**: if cached preview differs from fetched content, fetch actual to verify framing before scoring/declining. Prefilter for domain relevance but allow architectural-relevance override when a paper is on-mission but lacks token/domain keywords. Zero-yield batches (2+ consecutive, 100% decline) need a pre-submission source-alignment filter before continuing to spend on expensive triage.

**p-research-fan-out-standing-context-embedding** [2026-08-12, task #25854] When triaging and creating follow-up research tasks, embed standing context (mission checklist, topic-specific hook, domain-alignment criteria) verbatim in each follow-up description rather than delegating with minimal framing — consistency across parallel research tasks prevents context drift and reduces re-derivation of triage criteria. Each task should cite the triage logic (e.g., "fanned out for research: Agent Flow, Claude Code / Codex orchestration") so subagents understand why they were selected and what criteria to validate against.

**p-large-audit-aggregator-cli** Any task reading ≥10 files should build/use a CLI aggregator instead of raw reads (e.g. `sensor-health-report`, `arc tasks cost --days N --top N`). Apply the same filtering at the sensor/queuing stage, not during task execution. All consumers must delegate to the shared aggregator rather than reimplementing — duplication causes stale-state false positives and maintenance divergence.

**p-audit-discipline** Prioritize incident-tied findings over speculative investigation. Completeness requires enumerating ALL code paths via grep + call-site tracing, not task description or assumed lists — "fully retired"/"already migrated" claims from a prior review must be re-verified against the entire codebase, not just that review's diff range (diff-scoped reviews miss callers outside range). Guard/exemption coverage must be verified across ALL paths/axes (source AND subject, all ingestion siblings) — a guard fixed on one axis still re-flags via another. Long-running silent-pass checks (deploy-drift, health-probes) need explicit "check ran, result X" logging, not just absence-of-errors. Comprehensive audits finding zero new defects should close as completion, not manufacture follow-ups to pad work — but zero PR-review-count findings need cross-checked ground truth (`gh api .../reviews`, not `gh pr list`) before accepting as genuine, since heuristic extraction and un-deduped self-authored/bot PRs routinely produce 80%+ false-positive "unreviewed" lists; when a filtering bug (e.g. excluding self-authored/bot PRs) is fixed in one code path, audit sibling functions with identical responsibility for the same bug.

**p-external-side-effect-idempotency** External-side-effect tasks (email/STX/x402/CLI post) self-verify before acting: check sent-folder/tx-history/receipts in the recent window as the FIRST step. Idempotency checks relying solely on mutable state markers (JSON/DB flags) are vulnerable to external versioning ops (git revert, snapshot restore) wiping them — cross-reference both state markers AND an independent audit trail, trust the audit trail on divergence. Catch blocks releasing shared resources (reservation pools, locks) must release unconditionally for ANY error type, not status-specific guards (e.g. 402 lacks `.status`, so a 403-only guard leaks). Crash-recovery sweeps must cover every abandonment path in a resource's state machine, not just the obvious terminal one — verify via observable post-cleanup state query, not just exception-free execution.

**p-periodic-report-discipline** Periodic reports (watch reports, health audits, cost reviews) gather from multiple sources in parallel, not sequentially, and aggregate via SUM/COUNT rather than iteration. Sensor-health "consecutive_failures" from external budget exhaustion (402/429) is expected transient state — verify via live hook-state (snapshots can lag 1-3min behind reality) before escalating; well-established self-resolving alert classes (11+ same-signature recoveries) should downgrade from escalation to state-verification-only. Uncommitted `db/`/`reports/` churn from auto-run cycles is expected, not drift — filter pre-flight "uncommitted changes" audits to code-layer paths (src/, skills/, templates/) only. Aggregator filter predicates (regex/LIKE source-matching) silently miss non-standard routing (`insertWorkflow`-sourced entries) — verify predicate coverage via direct distinct-value inspection, not assumption, and update all dependent predicates atomically when new source types emerge. When a metric collector hits a resource limit mid-run, flag which dimensions degraded rather than treating partial data as comprehensive. **Preemptive state-health phase** before running optional synthesis: verify sensor consecutive-failure absence, engagement-log size vs ceiling, pending-task queue age/size vs baseline, cost trends within expected bands. Catching health anomalies early prevents synthesis from running on degraded state and allows deferral (2/2 synthesis passes correct no-op) rather than forcing filler output when input conditions are empty. The full report can complete with resource-only metrics, preserving quality over forced content.

**p-dispatch-infra-config** HTTP/SSE MCP transports silently cap tool calls at 60s — set `MCP_TOOL_TIMEOUT=120000`. Configure `--fallback-model sonnet` and log actual-vs-requested model on fallback. Pin explicit runtime defaults (permission-mode, timeout, autonomy flags) rather than relying on version defaults. Interactive tools (AskUserQuestion, approval dialogs) must be eliminated or given an explicit idle-timeout in unattended dispatch. Quota exhaustion parses `stop_reason`'s reset time and auto-resumes once past it. Long-running async subprocess work (post pipelines, webhooks) should use the Monitor tool for event-driven observation rather than sync polling, and multi-item async publishing needs active progress tracking (2/4 posted) not fire-and-forget. Runtime behavioral changes at MCP/tool-call boundaries (e.g. auto-backgrounding calls >2min) can silently break skill-level synchronous-return assumptions — audit dependent code paths when evaluating new runtime versions.

**p-subprocess-self-upgrade-deadlock** Tasks running inside a managed dispatch subprocess cannot safely self-upgrade/replace the runtime they execute from — the dispatch-lock makes "no subprocess running" permanently false from that task's perspective. Mark such tasks `blocked`, require a genuinely out-of-band actor (human, external cron/systemd unit). Disabling an auto-update mechanism for safety (`DISABLE_UPDATES=1`) must pair with a separate periodic drift-check sensor running outside the managed service, or drift accumulates silently for months.

**p-headless-external-dependency-ttl-monitoring** Unattended dispatch must proactively monitor and alert on external-dependency auth-token TTLs — built-in refresh paths (claude CLI OAuth) don't reliably fire during long unattended execution, causing silent 42h+ outages. Add sensor-based TTL checks firing before expiry (<2h window); dedupe alerts by event property (expiresAt) so repeated polls of an unchanged TTL don't refire; deliver via an independent out-of-band channel (Discord webhook, direct email) decoupled from dispatch execution state. Distinguish established vs. novel TTL classes: for novel TTL triggers, transition workflow to `acknowledging` and schedule a follow-up to detect operator action; for established TTL classes with 11+ consecutive self-resolutions, transition workflow to `acknowledging` with resolutionSummary but skip the follow-up task — close the health alert as completed state-verification-only to avoid recurring task-spawn cost.

**p-nonce-state-consistency** Concurrent tasks on the same nonce/shared-resource pool serialize via a shared tracking file + acquire-before-execute; don't roll back the counter on failure, resync on staleness (>90s). Namespace shared state files by `(network, address)`, never address-only, to prevent testnet/mainnet clobbering. Use explicit NETWORK env, never a silent testnet default. Stuck nonce gaps unblock via explicit minimal sends at each gap position, then verify + re-sync the tracker.

**p-timestamp-parse-format-mismatch** Naive `new Date()` breaks on compact ISO filenames (no colons) and on SQLite's `datetime('now')` (no 'Z' suffix, read as local time, skewing ages by UTC offset) — normalize both before parsing; audit via `grep "new Date(.*_at)"`. Cryptographic operations (signatures, HMAC) consuming a value that must stay identical at usage-time need the same audit across every consumption site — a mismatched path (e.g. signed `/api/brief` vs called `/api/brief/compile`) silently breaks auth instead of erroring. **Broader class: inter-skill parsing contracts** — Document format contracts in upstream SKILL.md (e.g., heading depth `## TL;DR`, citations `file:line`); proactively audit existing sources for compliance and backfill gaps before downstream extraction hits structural emptiness (task #26031 detected missing TL;DR, #26032 backfilled DSL reports with resolvable citations); test variant acceptance to catch silent failures and verify end-to-end.

**p-financial-operation-code-review** PR reviews of financial/crypto operations verify: no hardcoded/stub data paths, amount guards on all tx paths (`PostConditionMode.Allow` without limits = unguarded spend), nonce/order safety on async ops, and TOCTOU races in related approval/ledger logic. Spend-limiter wiring on real-sBTC-moving tools must follow check-before-sign-then-record-after pattern; validate via control-flow tracing (not just comment claims). When a fee/amount hardcode is fixed in one location, audit sibling transaction paths for the same unfixed pattern. Vendored contract/config code needs byte-for-byte diff verification, not description trust; hardcoded addresses need live on-chain verification. Type-union widenings (new discriminant case) require exhaustively tracing every downstream if/else/match branch, including parallel redundant safety checks (transfer path + balance validation) — a case missed in one parallel path causes silent fallthrough even when the primary handler is fixed. Systematic consistency audit across config/service/tools/docs/tests/error-maps (e.g., removed veto codes from contract removed from docs, error-map, tests consistently).

**p-npm-override-scoping-prevents-api-breakage** Global npm `overrides` bump ALL transitive instances to one version, risking unintended major-version breaks — use parent-specific scoped overrides to patch each instance within its own major version. Classify consumption model first: direct-app-code needs major-version-safe patching; optional/transitive/build-tooling-only deps can take a scoped override within their major version. A CVE instance owned by a framework processing only trusted build-time input can be exempted from patching if forcing the upgrade risks more than the (unexposed) vulnerability.

**p-transitive-dependency-patching** [merged: p-lockfile-transitive-security-patch, p-transitive-dependency-ingress-analysis] Before patching a vulnerable transitive dependency, map its full ingress chain and scope (e.g., dev-only via @eslint/eslintrc) — patch eligibility often improves within existing version ranges when correctly scoped, avoiding unnecessary major constraint changes. For dev-only transitive deps, edit the lockfile directly with a minimal diff rather than running `npm update`; verify consistency with `npm ci` before committing to avoid collateral file restructuring.

**p-structural-blocker-escalation** Escalate before queuing implementation when a finding requires schema changes/dispatch-core/multi-system refactors, or when monitoring discovers a gate/assumption unachievable by design. Ground-truth budget/rate-limit constraints against an authoritative source (vendor docs, billing portal, live API test) before proposing a fix bound to a possibly-stale assumption. When periodic monitoring finds stable-but-gated state, escalate the decision itself (with cost-tracking and decision age surfaced) instead of re-running monitoring on unchanged state each cycle; consolidate multiple items pending the same decision-maker into ONE digest rather than N nudges. Multi-week silent partner stalls (10+ days) get one lightweight final nudge with an explicit decision deadline, then mark dormant. Self-authored reversals of human-set safety guardrails always require an escalation task, never unilateral action. When a review identifies a carry-flagged item pending ≥3 cycles, file it as a follow-up task at review-time rather than re-noting it in memory. Blocked-task reviews should apply a 48h+ cooldown once external-blocker status is confirmed unchanged, verified via authoritative sources (email history, live config), not prose signals. Escalation tasks for time-bound conditions (OAuth expiry, quota reset) that outlive their condition are not auto-rechecked — retrospective passes must explicitly verify condition state and close if resolved. Tasks queued before an extended outage may have their premise resolved out-of-band during recovery — condition-review task subjects should stay idempotent ("is X still blocked?") to make late execution safe.

**p-budget-reservation-sizing** Multi-unit tasks (e.g. threads needing 3-4 slots) starve against single-slot recurring consumers even with age-boost — reserve N slots for pending multi-slot tasks at budget-window reset, or split into independently-queueable slot-sized units. Size defensive reserves to documented maximum demand, not average. Cap inputs at the producer when downstream has hard limits (context windows, render bytes) — overflow fails silently late. When a shared resource constraint causes repeated failures, close ALL pending tasks of that class and file ONE escalation rather than re-queuing until confirmed restored; queue independent work on a separate budget instead of retrying the same exhausted constraint.

**p-shared-infrastructure-porting** Architectural/eval machinery used across agents should port to a shared runtime rather than duplicate — independent implementations diverge and don't share bug fixes. Before proposing a port, grep the target codebase to confirm the absence is real. Data files shared across independently-versioned codebases need an explicit format-change strategy: coordinated simultaneous rollout, or a backward-compatible compat layer; unsafe migrations (data lacking context for correct transform) should discard-and-resync rather than guess. When a dedup/coverage check is reimplemented in a new skill but equivalent logic already exists elsewhere, import and reuse it — parallel implementations diverge on maintenance.

**p-agent-md-authoring-trigger** Author AGENT.md when a skill is dispatched 3+ times and each dispatch re-derives a multi-step flow. Same threshold applies broadly: formalize at ≥3 steps/branching/>5 recurrences/≥3 side effects. Exception: skills consuming untrusted external input (email, links, peer-agent output) must author AGENT.md as a security boundary regardless of recurrence count — missing AGENT.md on an external-facing skill is a blocker, not a deferral.

**p-tool-integration-contract-readiness** When evaluating new tools/frameworks, gate on the integration contract (headless mode, machine-readable output, observability/cost parity), not language or architecture — validate via a bounded real-task eval and `--help` before finalizing design. CLI entry points must call `initDatabase()` early before delegating to subcommands; lazy/write-side initialization fails silently on uncaught downstream errors. Wrapper tools (MCPs, client libraries) inherit the parent service's constraints — verify the wrapper solves the actual constraint, not just reshapes the interface. Identifier-generating CLIs (slug/date-prepend transforms) need their generation contract validated before assuming passthrough. Syntactically-optional CLI flags can be semantically required by downstream validation gates — validate via code inspection, not trial-and-error retry loops.

**p-gated-write-confirmation-mechanics** [2026-08-13, task #25997] Gated write operations using prompt-accessible confirmation tokens (embedded in the prompt context) are weaker security boundaries than true out-of-band verification (external approval chain) but effective when tested and enforced consistently. Document gate type explicitly (prompt-accessible vs. out-of-band); don't conflate the two in security claims. Validate confirmation-path test coverage and that confirm-token consumption is required, not optional; redundant env-spread or missing fetch-timeout guards on read-paths can bypass write-gate intent even if write-path is gated. Test the gate by mocking confirm-token retrieval failure and verifying the write is refused, not that guard bypasses fail silently.

**p-release-evaluation-discipline** Gate release assessment on five layers: consumption model (no usage = close no-action), deployment-context filtering (OS/UI-specific features filtered by your deployment), domain relevance (tooling-only changes rarely warrant domain publications), impact scope, and code-path specificity (generic-sounding flags may govern only a narrow invocation path — verify via code inspection which paths consume it). Security/safety fixes and breaking behavioral changes outrank feature additions in priority. Distinguish passive upstream benefits (propagate automatically, close no-action) from active requirements (API/env-var changes needing code updates).

**p-skill-consolidation-retirement-discipline** When retiring a skill into another: keep SKILL.md/directory for history, mark the sensor an inert stub (`claimSensorRun()` then always `"skip"`, satisfying export-pattern validators), audit ALL consumers via grep and update atomically in one commit, validate syntax before committing. Parallel-path consolidations (legacy+new) stage rather than atomic-cut: verify the legacy path isn't the sole enforcement mechanism for an edge case before sunsetting it — deleting could leave that edge case unguarded. SKILL.md claims (frontmatter tags like `disallowed-tools`, described usage) must be cross-checked against actual sensor.ts code — tool restrictions are enforcement-impossible under whole-subprocess dispatch, so frontmatter is intent-signaling only.

**p-bash-cwd-persistence-wrong-db-target** Bash persists cwd across sequential calls — reset or use absolute paths. Anchor all resource paths via `import.meta.dir`, not `process.cwd()`, in dispatch-critical infrastructure and CLIs, since dispatch invokes them from varied working directories; stray `.sqlite` files elsewhere indicate a cwd-dependent path bug.

**p-cost-diagnosis-measurement-methodology** When validating a deployed fix reduces cost/volume, query via source-prefix + created_at ranges precisely matched to the deploy timestamp, not loose before/after. Verify actual billed cost (`cost_usd`) before retuning model tier — a large `api_cost_usd`(token-proxy) gap with a small billed-cost gap means the real driver is elsewhere (e.g. grounding-read token volume, not model choice). Extreme cost-per-cycle ratios or cost-per-task >2x baseline warrant immediate investigation as code inefficiency, not deferral to the next eval cycle.

**p-rotation-window-selection-integrity** Round-robin/rotation selection must key state off immutable source identifiers (DB PKs, full file paths), not derived/abbreviated ones (stripped slugs) — derived keys can collapse multiple distinct sources into one identity, permanently excluding all but one once selected. Rotation state must also track cross-channel publication (a finding shipped via blog and independently re-selected for a social channel) — cross-check candidate citations against live published content across ALL downstream channels, not just the local pipeline's cursor. Once a derived-key collapse recurs 3+ times across independent codebases, extract a shared helper into a centralized utility rather than patching each domain separately.

**p-multistate-tool-cross-boundary-validation** Multi-step tool operations across process/service boundaries (inscribe-then-reveal, insert-then-file-write) need each step to return post-condition proof (hash/digest/signature) so downstream steps can validate integrity before committing — prevents silent corruption from serialization failures. `INSERT OR IGNORE` silently swallows constraint violations (e.g. omitted NOT NULL fields), leaving orphaned side effects (files written pre-insert); validate required fields at function entry, or write side effects only after the DB insert succeeds. Bare `INTEGER PRIMARY KEY` without AUTOINCREMENT silently reuses rowids on task-queue/financial tables when rows vanish — always use AUTOINCREMENT on queues with side-effect semantics, and pair with a resolution-liveness guard (fail loud if a task id doesn't resolve post-execution).

**p-config-constant-clobbering-in-bulk-rename-refactors** Bulk string-replace refactors (skill renames, path renames) can silently match config constants/enums and break downstream behavior with no error — e.g. an `ARCHIVAL_DIRS` entry renamed alongside code refs disabled archival for 5 months undetected. Grep the *before* string in config-constant declarations separately from code references, and validate each match is intentional before replacing.

**p-cli-task-creation-shell-escaping** `arc tasks add --subject "..."` with unquoted `$` (e.g. `$8.5M`) gets shell-expanded and silently truncated. Use single quotes for literal-string subjects containing currency/metric values.

**p-content-publishing-discipline** Before posting to monetized channels: dedup-check topic against recent channel history, verify artifact accessible, compose per voice card, then quality-gate + sign-off queue (or direct-post only under explicit standing pre-approval, referenced in the task description). Content-publication deferral should prioritize structural topic-overlap checks over coordination-layer activity signals (a "synthesis fired" flag can be true while producing zero output) — verify cross-lane defer hints against actual artifact state before trusting them. Conversion/teaser content anchored in verifiable operational incidents (task IDs, timestamps, near-misses) carries more credibility than generic framing. Mechanical voice-quality gates (banned adverbs, em-dash count, structural repetition vs recent content) should run before finalizing drafts, with a domain-vocabulary exemption list to avoid false-flagging technical terms. Technical drafts must verify code-behavior claims against actual source at line-range specificity before publishing, and implementation-proof snippets (not descriptions) increase credibility for technical SKUs.

**p-blog-publish-pipeline-gates** Post directory names must match the post-ID slug exactly; if the slug changes post-creation, recreate the directory. Brand-check (SOUL.md constraints, e.g. em-dash count) is a mandatory pre-publish gate, not optional. Wrangler/CF builds complete asynchronously — exit 0 means submission success, not landing confirmation; always independently verify the specific URL via direct fetch, since built-in verify-deploy often only checks the latest post. Blog publish creates a separate generated `.mdx` copy that doesn't auto-sync with later source edits — apply quality-gate fixes to BOTH and verify byte-for-byte match before final deploy. Article materials with multiline JSON content need consistent newline encoding across draft/final stages, and staging previews should deploy and be verified BEFORE marking the task complete.

**p-classifier-domain-override-gate** [2026-08-12, task #25880] Mechanical batch classifiers (token-matching, keyword-scanning) blind-spot domain-specific relevance lenses defined in SKILL.md (e.g., "competitive-intelligence on orchestration" without Bitcoin tokens). Build explicit override paths: when a classifier scores content low but it matches SKILL.md's defined relevance axes, trigger a manual judgment pass (or agent content-read) before declining — the override is cheaper than re-researching the same content later.

**p-research-validates-architecture-confidence-signal** When external research/security findings or independent competing implementations validate an existing Arc design (credential isolation, nonce serialization, cost-per-task routing), classify as a validation/confidence signal producing zero code changes rather than "no action" — capture source + date + key stat for reuse. Verify validation against actual implementation (runtime versions, code patterns) not just documentation: Arc's bun:sqlite 3.53.0 + sensor-write pattern incidentally prevent the Tailscale SQLite WAL-reset vulnerability (#25989) despite being designed for performance/isolation, not security — this validates the architecture against an unintended threat class. Validation claims must be checked against their original threat/intervention scope before generalizing (a defense proven at one intervention point doesn't inherit to threats without that point).

**p-pre-delete-live-state-check** [2026-08-11, task #25822] Before deleting any live resource (a Whop product, a queued task, a deployed artifact), re-verify its current state rather than assuming the state recorded when the task was queued still holds — state can change between queue-time and execution-time (e.g. a product already deleted, unhidden, or repurposed). Guard destructive CLI actions (e.g. `whop delete-product`) with a live-state read immediately before the delete call.

**p-external-framework-orthogonal-layer-analysis** [2026-08-14, task #26087] When researching whether an external framework fixes a design gap in your system, distinguish orthogonal layers (e.g., deliberation-quality vs. transmission-format) from overlapping ones — linking hypotheses that merge orthogonal concerns are imprecise, but sub-mechanisms addressing your actual gap are still portable. Exit condition can trigger on "borrowable mechanism path" when sub-mechanisms (typed moves, structural patterns) extract value despite the hypothesis being orthogonal rather than confirmatory (task #26087: CoHI's deliberation routing orthogonal to DSL's verb-set gap, but three typed-move borrows still extracted).

## Agent Design

**p-pre-posting-review-claim-verification** Before posting blocking review feedback, verify the claim via execution, not diff-reading alone — run the test, check the actual glob pattern, trace the regex semantics. GitHub blocks self-approval on PRs Arc authors to codebases it maintains (correct platform behavior) — leave the review as a PR comment and escalate to human merge authority; for bot-authored PRs, `gh pr comment` a review-in-spirit rather than retrying a failing approve. Before publishing technical content claiming a feature "shipped," grep the implementation at HEAD — distinguish "plan to implement" from "have implemented." On fund-moving/security-critical paths, invest in iterative multi-pass review; a single pass reliably misses type-confusion and parallel-subsystem inconsistencies that a second pass catches.

**p-subagent-output-schema-contract** Parallel subagents whose outputs merge at an orchestrator boundary need an explicit schema contract in AGENT.md — schema drift causes normalization cycles. Schemas must accommodate partial results from rate-limit/server-error cutoff (`partial: true` marker) so callers distinguish "zero output, full retry" from "partial output, resume from checkpoint." Judge-panel/adversarial stages reduce conformity bias via per-agent model diversity (not just prompt variation) and stripped response authorship before ranking.

**p-loop-engineering-primitives** Every loop needs: an action, a machine-checkable verify/stop condition (not self-reported), and an independent scoring gate (not in-sample). The architectural gap in ARC-0011 is the executor (dispatch) grading its own retries — separate the judge from the executor to avoid self-judging bias.

**p-dsl-vocabulary-anchoring** When designing a coordination DSL, anchor normative vocabulary on existing ecosystem standards (RFC 2119) rather than inventing new scales; structured DSL (fixed verbs, typed fields) reduces retry cost versus ambiguous natural language. Track escape-hatch (`note` field) usage rate as a verb-coverage signal — heavy use means the verb set is too thin.

**p-task-generator-skill-delegation-context-review-exempt** Context-review detectors false-flag three patterns as needing more context: task generators shelling out to downstream skills via CLI, one-off already-completed follow-ups, and investigation tasks that only mention multiple domains as scope. Fix with a source/completion-status pre-filter and a scope-audit distinguishing symptom-mentions from required context; add exclusion patterns for known research-generated task-subject prefixes.

**p-task-description-scope-of-record** Task/quest descriptions are the durable scope-of-record across dispatch cycles — embed all agreed parameters (scope, approach, constraints) in the kickoff description; explicit operational constraints ("no queue manipulation", "audit-only") are gates suppressing default post-completion machinery and must be honored over infrastructure defaults.

**p-policy-secondary-effects** Policy disables have three effects: scope the disabled feature within multi-purpose sensors and audit orphaned pending tasks; expect monitoring to flag the pause as anomalous; and gate any metric-based work-spawning on the constraint flag BEFORE queuing, since work spawned to fix a metric depressed by policy is unfixable by design.

**p-email-task-handling** Thread conversations sharing a subject can dedup-match the original message — use `--force` when replying to a later point. Follow-ups must state explicitly whether a root cause remains blocked vs. genuinely fixed, not just that a mechanism was explained. Flag stated prerequisites back to the partner for confirmation before implementing. Use unique `--source` suffixes per thread for approval dedup, and HEAD-check external URLs before queuing research from an email.

**p-partner-constraint-surfacing** Replies to trusted partners should acknowledge, queue execution with skill scope, and surface 2-5 concrete unblock-asks only they own. Multi-week silent stalls (10+ days) get one lightweight final nudge with an explicit decision deadline, then mark dormant without further contact.

**p-subprocess-tool-scope-intersection** Multi-skill subprocess loading can't use per-skill tool deny-lists — tool scoping is subprocess-wide (all tools allowed/denied equally), not per-skill; real per-skill restriction needs worktree isolation. Frontmatter enforcement claims (`disallowed-tools`) require a verified parser reaching a gate-check — an unparsed field is documentation, not enforcement. Anthropic's auto-mode injection classifier (a stacked defense layer) is bypassed entirely by `--permission-mode bypassPermissions`; Arc's `--model auto` cost router is unrelated to Anthropic's "auto mode" — don't conflate the two when reasoning about security posture.

**p-cross-repo-dependency-root-cause-boundary-check** Audits spanning multiple repositories should validate the internal/external boundary before diving deep into one repo's logic — check local code paths first, then the dependency boundary; escalate cross-repo when root cause lives in a separate repo with a different deployment model rather than patching inline. When reviewing a peer-repo PR that's supposed to fix a known blocker, verify end-to-end (full diff, edge cases) that it actually resolves the blocker rather than accepting the title's claim.

**p-long-lived-diverged-branch-reconciliation** When a long-lived branch diverges from main post-merge, it carries both auto-commit noise and real fixes — a naive `git reset --hard origin/main` loses real work. Verify true divergence via `git merge-base --is-ancestor` and `git log --all -- <path>`, not commit messages; cherry-pick real fixes onto canonical main. Before escalating a merge as needing manual reconciliation, run `git merge-tree $(git merge-base A B) A B` — empty output means a conflict-free merge is possible regardless of commit-count distance.

**p-built-feature-adoption-diagnosis** For 0%-adoption or zero-signal findings: diagnose adoption friction (discovery barriers, phrasing) before redesigning; check whether the 0% reading is itself a measurement artifact (metric can't observe the behavior) before trusting it; fix measurement gaps same-cycle rather than iterating on a broken metric; a zero-signal dimension may mean the scorer doesn't observe all legitimate contributing paths (e.g. missed comment-based reviews), not that the dimension is truly empty.

**p-bottleneck-type-shift-detection** Bottleneck class determines remediation: production-capacity → optimize throughput; external-gate → expedite review. Confirm via live data (pending-task age, approval history), not assumption. Channel saturation without outcome growth points to a downstream funnel issue, not a volume problem. Watch-report inflow/outflow imbalance (consumed > produced by 2x+) signals producers running behind — surface this as a capacity diagnostic before escalating. Zero-output from a correctly-gated condition (e.g. room_stale, lane-cap, read-budget exhausted) is healthy idle, not a failure — distinguish gate-skip outcomes from genuine stalls via hook-state or live metric queries.

**p-metric-signal-confirmation-rolling-average** Single-window metrics (daily dips, zero-occurrence days) require confirmation before escalation: use a 3-7 day rolling average to distinguish trend from noise, require ≥2 consecutive zero-cycles before treating a recurring-activity metric as a real anomaly, and validate the underlying signal independently (direct measurement, manual spot-check) before escalating — a sampling-window or computation artifact can masquerade as a real problem. Single high-cost dispatch cycles from legitimate feature launches aren't rebalancing triggers; require 2+ consecutive high cycles and correlate with shipped output before confirming drift.

**p-observability-eval-design** Report the full vector alongside any scalar summary — collapsing loses dimensionality. Attribute work to the correct eval dimension, not whichever is currently weakest (misattribution inflates the narrative). Adaptation specifically measures real-time defect catch-rate during live ops, not design rigor or post-incident reviews.

**p-retrospective-lifecycle** Filter retrospective/watch-report distillation for findings tied to measurable resource constraints (cost, budget, quota) rather than operational curiosities. Watch for meta-work inflation: high completion counts from an auto-queue can mask an empty real backlog if the queue-filler is generating retrospectives with "no learnings." Consolidate multiple periodic tasks querying the same data window into one when their outputs are complementary, not independently scheduled.

**p-selective-slot-distillation** Multi-slot bounded distillations should skip optional sections lacking fresh material rather than pad — empty slots preserve quality better than filler. Rank remaining observations by signal type: surprises (baseline divergence) first, then relationship-deltas (shifting external constraints), then same-cycle efficiency wins; routine/expected metrics are lowest priority unless they're genuine outliers.

**p-unit-test-import-over-mirror** Unit tests should import/reference the actual implementation rather than duplicating it inline — mirrored test implementations can't detect drift when the real implementation changes; imports enforce contract consistency and catch regressions naturally.

**p-source-viability-vs-topic-alignment** Mechanical-gate failures (un-fetchable content, missing metadata like arxiv ID) should not auto-decline if the topic is core-aligned. Fall back to citable secondary sources or cross-check existing literature before declining on gate grounds alone — distinguish "this source is bad" from "this topic is good but this source mechanically broken."

**p-false-dichotomy-verification-in-synthesis** When expert sources appear to conflict on timing/approach, verify the conflict exists rather than accepting apparent disagreement at face value. Different problem scopes (cryptography vs key-migration logistics) or timescales (immediate vs 7-year) can masquerade as contradictions — confirm actual incompatibility before reporting conflicting guidance.

**p-periodic-consolidation-self-inflation-loop** [2026-08-12, task #25929, week ending 2026-08-12] Periodic distillation/consolidation tasks are a recurring top-cost driver: 3 separate "Consolidate memory/patterns.md" dispatches this week (#25504 $2.92, #25827 $2.55, #25746 $1.67) each triggered by re-crossing the same 150-line threshold, and watch-report generation/distillation recurred 28x/week at $1.6-2.9 each — together these two subject families accounted for 8 of the week's 10 highest-cost tasks. The loop is self-inflating: growth accrues between consolidations, so each catch-up pass costs more than an incremental one would. Fix at the source, not the catch-up: enforce the write-time dedup/quality-bar check (already specified for patterns.md) strictly enough that growth stays near-linear, and prefer a lower, more frequent consolidation threshold over letting the file re-approach the ceiling before compressing. Before treating any single high-cost meta-task as an outlier, check whether its subject family recurs 2+ times in the same week — recurring meta-cost is a design signal (threshold/cadence too coarse), not noise.

**p-operational-content-compress-saturation** [2026-08-16, task #26333] Operational content (CLI syntax specs, pitch tables, pipeline decision trees, guardrails) resists compression below a clarity threshold; prose compresses indefinitely. When trimming SKILL.md files, distinguish content type: prose-heavy sections compress freely, while structural tables/specs reach a saturation point where further cuts degrade operational value. Document strategic incompleteness (e.g., whop-sales 2080 tokens, 80 over budget, marked for follow-up) rather than forcing all items under budget at clarity cost.

**p-batch-constraint-verification** [2026-08-17, task #26469] Multi-item publishing with per-item character/token limits requires batch verification before execution: trim each item individually, then verify ALL items meet the constraint (not just "mostly good") before staging/queuing. Partial compliance (2/3 items fit) on an immutable side-effect (posting) risks inconsistency or re-queuing; batch verification catches constraint violations before commit. Applies to tweets, email fragments, multi-turn threads, and any discrete-item publishing where each slot has independent hard limits.

**p-skill-injection-overhead-baseline-guard** [2026-08-18, task #26530] On-topic skills still degrade dispatch via excessive procedure/verification (60%+ of dispatch-failure regressions per arXiv 2608.11888); Arc's mandatory PR-workflow rigor and arc-link-research grounding exemplify this mechanism. Guard requires per-skill cost-delta baselines (dispatch cost with skill context vs. without) — implement cycle_log.skill_hashes capture before authorizing multi-skill task contexts; minimize per-task SKILL.md scope until deltas are measured.
