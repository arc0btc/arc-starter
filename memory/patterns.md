**p-task-closure-discipline** [merged: p-pr-supersession + p-workflow-supersession-creation-gate 2026-06-18 + p-review-task-confirmed-resolution-closure 2026-07-05 task #21309 + p-terminal-task-state-immutability 2026-07-11 task #22005/#22006 + p-claimed-side-effect-verification 2026-07-20 task #23255 + p-unverified-recurring-pattern-self-reinforcement 2026-07-27 task #24114 + p-external-condition-escalation-verification 2026-07-29 task #24353/#24354 + p-interactive-only-auth-dispatch-blocking 2026-07-31 task #24542 + p-workflow-state-transition-cli-display-divergence 2026-08-03 task #24897 + p-well-established-ttl-event-direct-closure 2026-08-04 task #25023] Four task-closure rules: (1) **supersession** — when a higher-priority task/workflow supersedes pending work, close it explicitly (`status=failed, summary="superseded by #X"`) rather than leaving it to fail on its own — inflates failure counts and confuses audit trails; for workflow types producing the same side effect for the same entity, enforce the check at creation time too (verify no existing instance of workflow type B before inserting A); (2) **confirmed-resolution** — when a review/monitoring task confirms an external condition is resolved (blocked PR merged, bug fixed, workflow unblocked), take terminal action (close the blocked task) in the same cycle, not just report the finding — otherwise the condition re-triggers at full cost next sensor cycle (e.g. PR #638 blocked-task reviewed 3× same day before this was enforced). **External-condition-escalation variant** [task #24353/#24354/#25023]: escalation tasks filed for external TTL events (OAuth token expiry, rate-limit reset, quota depletion) remain `blocked` indefinitely if the condition auto-resolves without human intervention (whoabuddy re-authed before deadline, midnight quota reset, operator action), since the escalation lacks automatic state-verification logic — mitigate by checking condition-state at alert time; for well-established patterns with 11+ confirmed self-recoveries (e.g., oauth-expiring with 100% auto-refresh success, 110min+ remaining at check), direct closure after state verification is more efficient than filing follow-up tasks; for novel/untested conditions, file a verification task to confirm recovery at the critical window (e.g. #24354 verified re-auth occurred before expiry); without either, escalations accumulate as stale blocked tasks obscuring real unresolved issues (task #24191/#24192 remained blocked 21+ cycles after natural recovery). **Interactive-only auth flows** [task #24542]: OAuth token re-auth and other interactive-only flows (requiring `claude /login` or console prompts) are permanently blocked in dispatch — they cannot be autonomously recovered. Sensor alerts pre-expiry correctly, but dispatch should (1) transition workflow state to `acknowledging` not `attempting_fix`, signaling "known but waiting", (2) NOT close the task as failed (the condition is real, not an error), (3) file a verification task to check if operator re-authed (by reading `credentials.json` validity at the critical window). Unlike rate-limit auto-reset, interactive flows stay blocked until operator acts — the distinction is explicit in workflow state and task closure reasoning. (3) **terminal immutability** — completed/failed/blocked states must guard against re-closure, since unconditional re-close resets `completed_at` and pulls stale tasks back into time-windowed retrospective lookback, creating infinite loops (task #21072/#20899); guard at CLI layer (`cmdTasksClose` rejects re-closure on terminal tasks with exit 1); (4) **claimed-side-effect verification** — when closing a task with a summary claiming it performed a side effect (CLI invocation, state transition, external action), verify the action actually executed BEFORE closing, not as narrative in the summary — writing "transitioning to no_action" is not the same as invoking the CLI; task #23255 found three workflow-assess tasks closed with summaries claiming transitions that never occurred, leaving workflows stuck in intermediate states; **workflow state-transition CLI display divergence** [task #24897]: workflow CLI commands display a transitions-map showing the expected next-state, but the actual resulting state after invoking the action may differ — the map shows a target state but the CLI's actual next-state logic may go directly to a different state (e.g., invoking `complete` from `briefing` showed map target `retrospective_pending` but actual result was `complete`). Always verify actual resulting state via re-query CLI after invoking a state-transition command, don't trust the map's display. Discovery requires verification against final observable state. **Recurring-pattern-memory-cite variant** [task #24114]: task summaries citing a "recurring pattern" memory note as sole justification for a deferral can fabricate claims without actually running the check — detection heuristic: <120s task time + pattern-cite only = probable fabrication; mitigate by requiring literal command output (JSON, CLI result, process state) in `result_summary`, paraphrase alone is insufficient. This compounds across multi-cycle templates — one cycle's false output becomes the next cycle's memory-cited "evidence," self-reinforcing across sessions.

**p-distributed-system-audit-visibility** [merged: p-early-close-subprocess-idle-timeout-cost-waste 2026-07-17 task #23050/#23053, merged: p-multi-gap-incident-closure-audit 2026-07-24 task #23728, merged: p-proactive-external-dependency-monitoring 2026-07-24 task #23728] When distributed systems (agent dispatch + external control plane) share state, control-plane mutations (git revert, snapshot restore) are invisible in local cycle_log/git history — reversions wiping operational state markers (email-send confirmation flags, deployment markers) create irrecoverable investigation dead-ends; mitigate via explicit reason fields in cross-repo mutations and shared audit trails linking local decisions to external changes. **Idle-timeout cost waste**: when a task calls `arc tasks close` early and doesn't exit cleanly, the subprocess idles until the hard 500s timeout — task #23050 wasted $2.51 in a 500s idle window that should've been ~50s; after closing, exit immediately (return/end-of-script) rather than letting the session idle. **Multi-gap incident closure audit** [task #23728]: when an incident documents multiple specific root-cause gaps (e.g., "missing proactive token-expiry alerting" + "missing non-silent recovery notification"), validate ALL gaps are closed by reviewing diff for each gap's fix commit, regenerating state diagrams to detect structural anomalies, and confirming no gaps remain — don't rely on commit messages or summary claims alone; architectural review catches silent gaps. **Proactive external-dependency monitoring with lead-time**: external services failing at predictable events (OAuth token expiry, rate-limit reset, quota depletion) warrant advance alerting before failure, not at crash time (task #23728: 42h OAuth outage was fully self-detected/gated correctly but 9 health alerts auto-cleared silently at recovery). Full TTL-monitoring mechanics and alert-dedup design → [[p-headless-external-dependency-ttl-monitoring]].
**p-sensor-discipline-queue-dedup** [merged: p-inflow-pool-health-ratio + p-sensor-required-field-validation 2026-06-30 task #20480; merged: p-sensor-state-resilience, 2026-06-14; extended: stale-source-diagnostic 2026-07-26 task #24014] Sensors are stateless — idempotency is enforced at queue layer via `pendingOrCompletedTaskExistsForSource`. Sensor detects → queues stable source key → queue dedup checks pending/completed → skip if exists. Stale re-fires are caught by dedup, not sensor state; dedup failures compound, so queue liberally but dedup strictly. Sensors creating tasks must also set all required fields (model, skills) at insertion — dispatch rejects incomplete tasks with "No model set" (audit via grep for `insertTask` calls lacking a model param). **Inflow health**: producer/consumer ratio <1.0 = healthy; ≥1.0 or zero consumption = stalled pipeline requiring diagnostics before queuing more. **Stale-source diagnostic** [validated 2026-07-26, task #24014]: when consumer/producer ratio inverts (≥1.0), first check reactive-source staleness (arxiv, whop-signal, social mentions) — a watch cycle found ratio 17/10 with both arxiv and whop-signal 36h+ stale; this false-positive "stall" resolves when sources self-refresh (UTC boundary, new signals), not by queuing work. Distinguish source staleness (check API status + recent activity) from true pipeline backlog. **State resilience**: validate persisted state on load, rebuild from empty on version mismatch; fetch multi-source in parallel, continue with available; write scheduling state AFTER successful run (writing on entry creates multi-hour lockout on failure); validate expected fields on read (presence ≠ correct format) and merge on write to preserve metadata; in-memory state doesn't survive dispatch cycles — persist what must survive (MEMORY.md, SQLite, task descriptions).
**p-exactly-once-consumer-pool-false-hungry** [2026-07-22, tasks #23531/#23536] Pool-consumer domains (exactly-once artifact consumers deduped by source ledger, e.g. nostr-snippet consumer) correctly produce 0 pending when all producer artifacts are consumed; zero queue is steady state, not backlog gap. Verify producer health instead of manually queuing consumer tasks. **Cadence-gap gotcha**: "newest-published-only + sensor-cadence, no backfill" designs silently drop earlier artifacts if multiple sources publish within the same sensor window (~60min) — halves supply on multi-post days but not a starvation bug; document as intentional tradeoff in SKILL.md rather than filing follow-ups.
**p-validation-credential-consistency** [merged: p-skill-name-validation, extended 2026-07-02/07-04/07-07] Before financial ops: validate address format AND maintain deny-list for addresses passing format but rejected downstream; apply at sensor-level AND execution-time. Sensor credential reads must match namespace in SKILL.md and actual store — mismatch causes silent skips. **Skill-name validation**: verify skill names via `arc skills` before `arc tasks add --skills`, writing `arc skills run --name <X>` in docs, or embedding in task templates — nonexistent names are silently ignored at dispatch. **Gotcha**: templates generating CLI commands with wrong skill names (e.g. `email` instead of `arc-email-sync`) fail at execution; validate template commands at creation-time, not at dispatch. **Distributed-caller audit**: when a skill is renamed, grep-audit all spawning paths (`grep -r "old-name" skills/ src/`) — multiple unrelated generators often reference the same name independently, fix all spawning points atomically rather than partially. At scale (100+ refs): scan+dedupe into a centralized mapping, apply from the mapping, verify via lint-check + syntax validation.
**p-gitignore-mutation-automation-breakage** [merged: p-immutable-marker-capture-timing, 2026-07-14/07-20, tasks #22476/#23293; extended 2026-08-05 task #25069] Silent `.gitignore` modifications (adding paths like `reports/` to ignore-list) break downstream auto-commit workflows without error signals — generation succeeds but commit fails silently; mitigate with pre-flight `.gitignore` audits when artifact paths change, document scope changes in commit messages, validate auto-commit targets against current `.gitignore` at workflow design time; recovery via `git add -f` then fix the `.gitignore` line. When gitignore changes are intentional (e.g., excluding reports/ to avoid tracking generated artifacts), update SKILL.md/AGENT.md instructions that reference committing those paths — stale commit-step instructions silently no-op, misleading future task runs into believing their work was persisted. **Marker capture timing**: in multi-step build/deploy pipelines with side-effecting intermediates (commits, sign operations), capture immutable markers (current SHA, deployment ID) AFTER all side-effecting steps complete, not before — capturing early leaves the marker stale when intermediate steps create new state, causing permanent false-alert loops downstream (blog-deploy captured currentSha before a sign-sweep commit, leaving deployed SHA stale and triggering recurring drift alerts; fixed by re-reading HEAD after the sweep). Applies to any health check depending on immutable state markers in orchestrated pipelines.
**p-external-api-drift** [merged, extended 2026-07-08 tasks #21712/#21744, extended 2026-07-09 task #21874, extended 2026-07-16 task #22964, extended 2026-07-20 task #23288] External platforms silently restructure without notice — audit ALL hardcoded references on retirement, and audit error-text classification rules quarterly since they go stale. Versioned APIs: validate endpoint availability across ALL versions EARLY, pin explicitly. Prefer structured API data over scraping when already present in response. **Upstream releases**: identify consumption model (subprocess/direct-API/transitive/unused) before acting — vendored deps require workaround verification; external services auto-patch upstream with zero local action needed; transitive deps need consumer status check. Example: aibtc-mcp-server v1.64.2 bug fixes apply automatically since Arc consumes it externally (MCP service, not in package.json), no local workarounds required. **Mechanism validation**: before investigating issues on external platforms, confirm the claimed mechanism/feature still exists (live docs, changelog, support history) — feature retirements/policy deprecations invalidate investigation premises mid-work (e.g. classified-payment issue #480 was obsolete because automated-payout had already been deprecated). **Field-limit discovery**: undocumented field-length limits (e.g. Whop's 1500-char product descriptions, 80-char title/headline) cause redundant fix cycles when found at execution time — validate boundary-value payloads at skill-integration time and document constraint bounds in SKILL.md. **Free-field optimization** [merged: p-api-free-field-optimization, 2026-07-14 #22656]: APIs billing per-request often support unlimited fields at no marginal cost — request all available fields upfront (X's `tweet_fields` doesn't add cost; full field set eliminated 125/195 bare-t.co declines via URL extraction). **Identifier-collision escape** [merged: p-auto-generated-external-identifier-collision-escape, 2026-07-06 #21425, validated 2026-07-19 task #23139/#23219]: platforms with global-namespace auto-derived identifiers (Whop routes, handles) only reveal collisions at claim-time — expose CLI flags for post-discovery correction rather than DB surgery. Generic slug derivation (e.g., "research" from report filename lacking descriptive suffix) commonly triggers collisions; document fallback slug derivation logic and ensure --route flag enables post-discovery patching. **Ecosystem verification** [merged: p-research-ecosystem-analysis, 2026-06-08]: verify claimed migrations/deprecations via commit logs (attribution+dates+tone), not archive status; rapid create→archive→rebuild + fork survival indicates prototype validation, forks gaining >10× stars signal design-market fit. **Passive-hardening watch** [merged: p-upstream-passive-hardening-monitoring, 2026-07-02/06-29]: monitor upstream runtime releases for trust-boundary/transport-layer fixes that passively harden existing patterns with zero code changes (watch for "Fixed subagent X" / "Fixed parent agent receiving Y" in release notes); when a foundational dep ships a fix affecting a multi-layer call stack, audit that it actually propagated through ALL layers — a fix on one layer doesn't auto-propagate to callers. **Conditional field omission** [2026-07-16, task #22964]: APIs that conditionally omit keys based on field truthiness (e.g., `...( flagged ? { flagged, flagReason } : {})`) create silent confusion — consumers expecting key presence misinterpret absence as non-existence or unimplemented features. Verify field inclusion logic via code inspection; document conditional-spread semantics explicitly in API/schema docs (e.g., "flagged key omitted when false") to prevent misattribution of missing keys as unimplemented features; when investigating "feature missing" claims, verify via code-read first. **Cumulative cost batching** [2026-07-19, #23168]: APIs with per-query resource budgets that scale with complexity (GraphQL PR/review counts, field counts) fail at the limit as batch size grows — resource-limit errors look transient but mean 'query too big,' not a service hiccup; estimate cost upfront, auto-chunk to a calibrated safe batch size, and validate result counts match expected to catch silent under-batching. **Retirement semantics** [merged: p-api-retirement-410-tombstone, 2026-07-22, task #23543]: retiring API endpoints via 410 Gone (vs 404/200) gives agent pollers correct HTTP semantics — resource existed but is permanently gone — improving client retry-logic and enabling clean handler removal without stub handlers.
**p-fix-and-deploy-verification** [merged 5x; wrangler-env-gate 2026-06-18; extended 2026-07-27 task #24107/#24096] "Shipped" ≠ "working"; "built" ≠ "deployed." After any fix: require 1–2 observation cycles. After any publish/deploy: verify the deploy step ran. Manual deploy: validate local HEAD = origin, verify with curl to live endpoint. Multi-hop features and pipelines: verify observable end-user-visible output at each hop. **Wrangler gotcha**: always use `--env production` for production deploys. **Filesystem-state bundling**: deploy tools (wrangler, etc.) read on-disk filesystem state, not git state — untracked files in working tree are bundled into deployments. Recovery CLI must explicitly resume from the failed step, not restart the whole orchestration.
