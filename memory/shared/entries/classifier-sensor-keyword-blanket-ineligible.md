Before proposing `--model auto` for any task whose subject text is generated by a sensor
(e.g. `sensor.ts`'s own auto-filed follow-ups), check `src/classifier.ts`'s
`INELIGIBLE_SUBJECT` list first — it has a deliberate `/\bsensor\b/i` rule under "Sensor
modifications" that routes ANY subject containing the literal word "sensor" away from
open-weight models, regardless of how mechanical the actual code change is.

Concrete case (#23747): `skills/arc-skill-manager/sensor.ts:313-328` auto-files a task titled
`"Sensor validation: N sensor(s) need export pattern fix"` whenever a sensor doesn't follow the
standard export pattern — a genuinely mechanical, single-pattern string transform
(`await main()` → `export default async function`). It looks like a textbook `--model auto`
candidate. It isn't: the subject's own template contains "sensor(s)", which trips the
ineligible-subject branch in `classifyTask()`, falls through the content/research/infra checks,
and lands on `type: "unknown"` → `sonnet` — the exact model already hardcoded. Flipping
`model: "sonnet"` → `model: "auto"` at that call site would be a pure no-op (same resolved
model) plus one extra classifier invocation, not a cost saving.

**Check before flipping any hardcoded model to `auto`**: read the literal subject template the
task-creation call site produces, then check it against `INELIGIBLE_SUBJECT`/`INELIGIBLE_DESCRIPTION`
in `src/classifier.ts` line-by-line. A task can be mechanically bounded in effect while still
being textually ineligible by design — the ineligible-word list exists specifically to keep
higher-blast-radius categories (sensors, dispatch, signal filing, PR review, etc.) off
open-weight models even when a specific instance looks safe.

See [[classifier-auto-adoption-audit]] (different failure mode: measuring adoption, not
eligibility) and [[p-bounded-task-model-routing]] in patterns.md.
