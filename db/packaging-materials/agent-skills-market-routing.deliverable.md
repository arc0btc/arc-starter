# Agent Skills as a Market, and the Compositional Routing Gap Arc Already Has

**TL;DR**
The agent-skill market rewards small sharp single-capability workflows with quality gates, which is exactly Arc's 4-file skill pattern, so Arc converges with the 62k-star thesis already.
The sharp gap is routing: Arc loads skills from a static per-task JSON array picked by whoever files the task, with no decomposition, no retrieval, no dependency planning, and at 129 skills that static choice now caps what Arc can attempt.
SkillWeaver names the fix (decompose, retrieve per sub-task, plan a DAG); a stripped version belongs in `agent-runtime` skill-manager, and the build pattern is a credible $9 Whop SKU.

**Key takeaways**

- The market signal is small and sharp, not large libraries. @bibryam's top-10 by stars shows obra/superpowers (228k), anthropics/skills (151k), mattpocock/skills (130k), and explicitly notes "6 of the top 10 are single-skill repos. Not huge libraries. One sharp capability." ().
- Skills are workflow plus quality gate, not just docs. addyosmani/agent-skills (62,813 stars) defines skills as "the workflows, quality gates, and best practices that senior engineers use," mapped to a lifecycle (DEFINE/PLAN/BUILD/VERIFY/REVIEW/SHIP) where "Skills also activate automatically based on what you're doing" ().
- Single-skill retrieval caps capability as libraries grow. @omarsar0 on SkillWeaver: "Real tasks rarely map to a single skill. They need several composed together, but most skill routing still treats the problem as picking one tool from a library." The system pairs "an LLM decomposer with a bi-encoder FAISS retriever and a dependency-aware DAG planner," benchmarked on CompSkillBench (300 compositional queries over 2,209 real skills). The thesis: "As skill libraries grow, single-skill retrieval quietly caps what an agent can do." ().

**Arc-alignment**

*Convergence on skills-as-market.* Arc's skill contract is the market structure described by addyosmani. `skills/arc-skill-manager/SKILL.md` defines the 4-file pattern: `SKILL.md` (required, under 2000 tokens, name+description+tags), optional `AGENT.md` (subagent briefing), `sensor.ts` (detect and queue), `cli.ts` (every action expressible as a command). Each Arc skill is one sharp capability with a checklist and a `disallowed-tools` quality gate for read-only skills. `ls skills` returns 129 directories (e.g. `bitcoin-wallet`, `zest-auto-repay`, `arc-link-research`, `whop`). This matches the @bibryam pattern: many small repos, each one capability, not one monolith. The addyosmani "skills activate automatically based on what you're doing" claim is the one thing Arc does NOT do, which is the whole gap below.

*The static-vs-compositional routing gap (the sharp finding).* Arc has no router. `src/dispatch.ts:216` `parseSkillNames()` does `JSON.parse(skillsJson)` on the task's `skills` column, then `resolveSkillContext()` (`dispatch.ts:225`) reads `SKILL.md` for each named directory and concatenates them. That is the entire selection mechanism. The array is authored by whoever creates the task: a human via `arc tasks add --skills s1,s2`, or a sensor hardcoding its own skill list. CLAUDE.md states this directly: "The `skills` column is a JSON array of skill names the dispatched Claude instance should load." There is no decomposition of the subject into sub-tasks, no retrieval ranking the 129 skills against the work, no dependency-aware ordering. This is exactly the failure @omarsar0 describes. At 129 skills the author of a task cannot know which skills compose for a given subject, so they either under-specify (missing context, the failure mode CLAUDE.md already warns about when follow-ups omit `--skills`) or over-specify (token bloat against the 40-50k budget). SkillWeaver's three pieces map onto Arc's gaps cleanly: LLM decomposer (Arc has none, the subject string is opaque), FAISS bi-encoder retriever (Arc has none, selection is exact-name-match against a JSON array), DAG planner (Arc has follow-up tasks via `arc tasks add` but no automatic dependency graph from a single query).

*Port to agent-runtime?* Yes, if anywhere. The skill-selection mechanism is shared-base concern, not Arc-specific. `/home/dev/agent-runtime/skills` holds the 12-skill fleet base (`skill-manager`, `workflows`, `scheduler`, `worktrees`, etc.). Note `agent-runtime/skills/skill-manager/` is currently an empty directory (no SKILL.md), so the canonical skill-manager today lives in arc-starter. A router that decomposes a task subject, retrieves candidate skills by embedding similarity, and emits an ordered skill list belongs in `agent-runtime` so every fleet agent inherits it, with arc-starter consuming it at `dispatch.ts:216` in place of the raw `JSON.parse`. Honest caveat: this is a real build, not a config flip. It needs an embedding index over all SKILL.md descriptions (the frontmatter `description` field is already the natural retrieval document), an embedding call per dispatch (cost and latency against the per-task budget), and a fallback to the explicit array when retrieval confidence is low. The DAG planner is the hardest part and the least necessary first: Arc already decomposes via follow-up tasks, so the high-value first slice is retrieval-augmented skill selection (suggest skills the author missed), not full DAG planning.
