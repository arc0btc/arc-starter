# Code Mode — code execution as the token-efficient MCP tool-calling pattern

## TL;DR
Four sources (Anthropic, Cloudflare, Hornet, Perplexity) converge on one move: stop exposing raw tools to the LLM; expose a typed API and let the model write code that calls it. Anthropic reports a workflow falling from 150,000 → 2,000 tokens (98.7% cut) by turning MCP tool calls into code in a sandbox. Arc already does the *orchestrator half* of this — every capability is a CLI verb (`arc skills run --name X -- cmd`), not 129 raw tools — but leaves the *intermediate-result* and *external-MCP* halves on the table; the convention belongs in `agent-runtime`.

## Key takeaways

- **The two costs Code Mode attacks** (Anthropic): (1) *tool definitions overload context* — clients load all defs upfront; "agents connected to thousands of tools need to process hundreds of thousands of tokens before reading a request"; (2) *intermediate results consume tokens* — every tool result passes through the model, e.g. a meeting transcript flowing through context twice = ~50k extra tokens. [anthropic.com/engineering/code-execution-with-mcp]
- **The fix: present MCP servers as code APIs, not direct tool calls.** Generate a file tree (`servers/google-drive/getDocument.ts`, each tool = a file wrapping `callMCPTool`); the agent discovers tools by listing the dir and reads only the defs it needs. Reported result: 150,000 → 2,000 tokens, "98.7%." [anthropic.com]
- **Why LLMs are better at code than tool calls** (Cloudflare): tool calls use special `<|tool_call|>` tokens the model only saw in a "contrived training set," whereas it has "seen real-world code from millions of open source projects." Their analogy: tool-calling is "putting Shakespeare through a month-long class in Mandarin." Cloudflare ships this as `codemode({system, tools})` in the Agents SDK, fetching the MCP schema and converting it to a documented TypeScript API at connect time. [blog.cloudflare.com/code-mode]
- **MCP's real value isn't tool-calling — it's uniformity** (Cloudflare): a standard way to connect, authorize (out-of-band), and self-document an API, so an agent can use a server "even if the agent's developers never heard of it." That uniformity is what lets the framework safely convert tools → sandboxed code API and still enforce a permission boundary.
- **Code Mode compounds across calls** (Cloudflare/Anthropic): chaining tools the traditional way feeds each output through the model just to copy it into the next input. Code skips that — loops, conditionals, filtering, polling all run in the sandbox; the model reads back only final results. Anthropic's spreadsheet example: filter 10,000 rows in code, model sees 5. Also cuts time-to-first-token (the `if` runs in the sandbox, not the model).
- **Progressive disclosure is the design primitive** (Anthropic): tools-as-files read on demand, *or* a `search_tools` tool with a `detail` level (name only / +description / full schema). This is the same lever as the harness ToolSearch/deferred-tool pattern.
- **Privacy/state bonus** (Anthropic): intermediate results stay in the execution env by default — data flows through a workflow "without ever entering the model's context" unless explicitly logged/returned.
- **Search/retrieval is the next layer** (Perplexity "Search as Code" + Hornet): the abstraction shifts from `search(query: str)` to `search(code: str)`. Perplexity reports single tasks invoking "hundreds or even thousands of retrieval operations within a few minutes"; they expose atomized search primitives as an SDK the agent composes in a sandbox. Hornet's sharp caveat: code mode "has to reach the primitives" — if recall is bad, no harness engineering recovers documents the primitives never surfaced. Their cited gap (BrowseComp-Plus): GPT-4.1 scores 93.49% with oracle docs vs 14.58% with BM25 over the *same* corpus — a 78.91-point retrieval-condition gap. Code mode amplifies a good retrieval layer; it cannot rescue a bad one. [research.perplexity.ai; hornet.dev]
- **Footnote (low value):** the `undefinedKi` tweet is an MCP *install* example (`claude mcp add --transport http moonchild …`), a designer-tooling thread, not a Code Mode source. Relevance ≤1 — noted, not analyzed.

## Arc-alignment — grounded in the repos

**Where Arc already does Code Mode (the orchestrator half — strong):**
- Arc's whole CLI-first principle *is* the "typed API instead of raw tools" move. The dispatched Claude is not handed 129 skills × their sub-commands as raw tool schemas; it's handed one surface — `arc skills run --name NAME -- …` — and writes invocations against it (`arc-starter/src/cli.ts:51`, dispatched via `Bun.spawnSync(["bun", cliPath, ...skillArgs])` at `cli.ts:604`). That is exactly Cloudflare's "turn the tools into an API the model writes code against," reached independently. CLAUDE.md's "every action must be expressible as an `arc` command" is the Code Mode thesis stated as policy.
- **Progressive disclosure already exists at dispatch.** `resolveSkillContext` (`arc-starter/src/dispatch.ts:225`) loads only the `SKILL.md` of skills in the task's `skills[]` array, and `filterMemoryBySkills` (`dispatch.ts:330`) trims MEMORY.md by skill tag. This is Anthropic's "load only the tools you need" — applied to *skill docs + memory*, not tool schemas. The 40-50k context budget (`CLAUDE.md:95`) is enforced by exactly this selective load.
- Arc runs *inside* a harness (this session) that already exposes deferred tools via ToolSearch — schemas loaded on demand. So the tool-definition-bloat problem is largely solved one layer below Arc, by the harness, not by Arc's own code.

**Where the gap is:**
1. **Intermediate-result bloat is unmanaged and only patched reactively.** MEMORY.md already records the symptom: "Per-file reads in dispatch = token explosion (>10 files → add CLI first)." That *is* Anthropic's "intermediate results consume tokens" problem, and Arc's own validated fix (add a CLI that filters/aggregates before returning, so the model sees 5 rows not 10,000) *is* the Code Mode answer — but it's applied case-by-case after a blow-up, not as a standing convention. There is no general "filter-in-the-subprocess, return compact evidence" idiom documented for skill `cli.ts` authors.
2. **`arc-link-research` is a retrieval skill with a fixed pipeline, not programmable primitives.** It exposes `prescreen | process | check | reindex | catalog` (`skills/arc-link-research/cli.ts`, 14 cases) — a monolith in Perplexity's terms. The agent cannot compose a task-specific retrieval loop (fan-out N queries, dedup, freshness-filter, keep survivors); it gets `process(links)` and a report. Hornet's warning applies directly: this report's own value ceiling is the retrieval primitives, and right now there aren't any to program.
3. **`arc-mcp-server` (agent-runtime) is the inverse direction and will hit this wall.** `skills/arc-mcp-server/tools.ts` exposes Arc's surfaces *as MCP tools to external clients* — currently 3 (`list_skills`, `dead_ends_read`, `dead_ends_write`). Small today, so raw tools are fine. But the moment it grows to expose the task queue + full skill tree, external agents pay the tool-definition tax. The skill's `harness-affinity` lists both `arc-starter` and `agent-runtime`, so the decision belongs in agent-runtime.

**Port to agent-runtime?** Yes — this is the headline call. `agent-runtime` is the lean shared base (12 skills vs arc-starter's 129; `src/skills.ts:78` `discoverSkills`). A fleet-wide convention — "skills present a typed API namespace; subprocesses filter before returning; arc-mcp-server serves a code API past N tools" — levels up *every* agent if it lands in agent-runtime, vs a one-VM tweak if it lands in arc-starter. arc-starter is where to *prototype* the intermediate-result idiom (it has the 129-skill blast radius to prove it); agent-runtime is where to *encode* it as the standard. No claim here is hand-waved: each maps to a cited file. What I could **not** verify: agent-runtime has zero `ToolSearch`/`mcpServers` references in `src/` (grep clean), so I cannot confirm how agent-runtime dispatch surfaces tools to its inner harness — that needs a follow-up read of agent-runtime's dispatch equivalent before designing the convention.
